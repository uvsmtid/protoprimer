TODO: TODO_87_26_62_66.clean_up_venv_driver_args.md

Remove redundant args from `VenvDriverBase` methods (and its `VenvDriverPip` and `VenvDriverUv` implementations)
which duplicate what the driver instance already holds in `state_local_venv_dir_abs_path_inited`.

See [venv_driver][FT_73_95_31_84.venv_driver.md].

## Why

*   `create_venv` / `_create_venv_impl` take `local_venv_dir_abs_path`.
    In production it is always the same value that the driver was constructed with
    (`state_local_venv_dir_abs_path_inited`).
    Unit tests pass different values, so they have to be updated.

*   `get_install_dependencies_cmd`, `_get_pin_versions_cmd` (and `install_dependencies`, `pin_versions`) take `venv_python_file_abs_path`.

    *   `VenvDriverUv`: the arg is ignored (the code uses `self.venv_python_file_abs_path`) - it is dead.

    *   `VenvDriverPip`: the arg is the only source of the python path (no `self.venv_python_file_abs_path`).
        Production callers pass `get_path_to_curr_python()` (= `sys.executable`),
        which equals `venv/bin/python` only when the process already runs inside that `venv`.

*   `VenvDriverUv` has a `NOTE` about the `venv_python_file_abs_path` arg being
    a `python` exec path internal to `uv` which fails if used directly.
    It describes the risk of passing a resolved/base interpreter path (e.g. `get_path_to_base_python()`) -
    `uv pip --python <base-interpreter>` would target the base install instead of the `venv`.
    (To be re-verified: it was not reproduced as a currently happening problem.)

## What to do

*   Move `state_local_venv_dir_abs_path_inited` and a derived `venv_python_file_abs_path` into `VenvDriverBase`
    (or add an abstract accessor).

*   Drop `local_venv_dir_abs_path` from `create_venv` and `_create_venv_impl`.

*   Drop the python path arg from `get_install_dependencies_cmd`, `_get_pin_versions_cmd`,
    `install_dependencies` and `pin_versions`: use `self.venv_python_file_abs_path`
    (`install_dependencies` also builds `PATH` from `os.path.dirname(venv_python_file_abs_path)` - adjust it too).

*   Decide on `install_packages(selected_python_file_abs_path)`:
    it takes a scratch `venv` python (used to install `uv`) - keep it with an explicit meaning.

*   Update the unit tests (`test_VenvDriverBase`, `test_VenvDriverPip`, `test_VenvDriverUv`) and remove the TODO-s and the `NOTE`.

## Considerations

*   Pros: smaller API; the arg cannot disagree with the driver's `venv`; the `uv` foot-gun is removed.

*   Cons / risks:

    *   Signature break for tests (and any external callers of the kernel API).

    *   Today the bootstrap flow passes `sys.executable`: installs target whichever python is running.
        Using `self.venv_python_file_abs_path` changes the target interpreter if boot ever runs outside the `venv` -
        run slow integrated tests for both drivers.
