Check that the `python` used to create the scratch `venv` (where `uv` itself is installed) is suitable for `uv`.

## Why

*   `VenvDriverUv._ensure_uv_is_available` installs `uv` into a throwaway `venv` (`uv_venv_abs_path`)
    using `VenvDriverPip` with whatever `python` is currently selected (`selected_python_file_abs_path`).

*   The scratch `venv` intentionally ignores `required_python_version` (`enforce_version_match=False`) -
    it is not governed by the project's `version_constraints.txt`.

*   But nothing checks that this `python` is new enough for `uv` itself.
    If it is too old, `pip install uv` fails (or installs an incompatible version) with a confusing error
    instead of an explicit message.

*   Find the minimum `python` version supported by the `uv` package (to be checked - do not hardcode a guess).

*   Assert it before creating the scratch `venv` and fail with a clear message
    (what `python` was selected, what is required for `uv`, and how to switch to `VenvDriverType.venv_pip`).

*   Decide where the minimum lives: a constant next to `ConfConstGeneral.name_uv_package`.

*   Remove the in-place TODO (and the `see TODO above` reference in the comment below it).

## Considerations

*   Pros: explicit failure instead of an obscure `pip` error.

*   Cons / risks: a hardcoded minimum becomes stale as `uv` evolves - keep it in one constant and cover it with a test.
