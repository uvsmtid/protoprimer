## Background

At the moment, the required environment is not selected automatically.

So, if you call bootstrap twice:

*   with `--env` arg:

    it bootstraps with the required environment config

*   without `--env` arg:

    it fails because the default environment config is selected conflicting with the current symlink

This originally proposed three prose-only approaches (A: make re-evaluation deterministic so `--env` is never
needed; B: always trust the existing symlink; C: both). None of those is what got decided - see `## Spec` below.

## Spec

[FT_03_31_63_70.environment_selection.md] is the authoritative spec, specifically its `## Conflict` table: outcome
per `_ExecOperation` x whether an environment is already persisted (`local_env_link` exists) x whether the
resolved value matches what's persisted.

That table is scoped to the relationship between the **persisted** value (the symlink) and the **selected** value
(whatever `_select_client_local_env_dir_any_path` resolves to) - **regardless of whether the env-selector hook
from [TODO_41_10_50_01.implement_env_selector.md] exists or not**. Today, "selected" can only come from `--env`
or the static default-env field; once the hook lands, it becomes a third possible source - but the table doesn't
care which source produced the value, only whether it matches what's persisted. So this doc can be implemented
now, ahead of and independently from the hook.

[FT_03_31_63_70.environment_selection.md]'s `## Path` section adds a general rule on top of the table:
`protoprimer` never builds paths through the `local_env_link` symlink - it only uses the symlink's **value** to
compose direct paths to the env config data (so that e.g. `op_eval` works without the symlink). This does not change
the table's logic (what to do on a mismatch per `exec_operation`), only what the node returns (see `### Design`).

**Decided** (recorded in [TODO_41_10_50_01.implement_env_selector.md]'s "Precedence" sub-section): no automatic
reconciliation. `op_reset` is the only exec operation that deliberately overwrites a mismatching persisted env;
`op_eval` evaluates the resolved value without touching persistence at all (`override`); every other op that
needs the env already correctly persisted (`op_boot`, `op_start`, `op_shell`) fails loudly on a mismatch.
[TODO_53_40_17_68.default_env_config_vs_lconf_symlink.md] asked the identical precedence question independently
and is superseded by this same resolution.

### Default env is a fallback, not a selection

**Status:** TO_FIX in PR C (spec decided in [FT_03_31_63_70.environment_selection.md] `## Default`/`## No environment selected`)

**Description:**
The default env (`field_default_env_dir_rel_path`) does **not** take part in selection: it is only used when
nothing is selected **and** nothing is persisted. "Selected" comes only from `--env` (and, later, the env-selector
hook). Today `_select_client_local_env_dir_any_path` folds the default into "selected", which makes
a persisted env that differs from the default fail on `op_boot`/`op_start`/`op_shell` without `--env` (this
TODO's original bug). With no env selected:

*   `local_env_link` exists: use its value (all `exec_operation`-s, including `op_eval` and `op_reset`).
*   `local_env_link` is missing:
    *   default configured: use it;
    *   default is `None` (may be configured so): use the global config dir (`state_global_conf_dir_abs_path_inited`),
        not `ref_root`.

**Decisions:**
*   Only `op_boot` and `op_reset` create/write `local_env_link` (for a selected env and for the default as well).
    `op_start`, `op_shell`, `op_wrap`, `op_eval` never create it (today `op_start`/`op_shell` do - to be fixed).
*   The "default is `None`" wording in the spec stays (it can be configured as `None`).
*   The "use `eval` for description" warning for a missing default goes away: `None` is a legitimate value.
*   The global config dir (`field_global_conf_dir_rel_path`) defaults to `ref_root` when not configured (was
    `<ref_root>/gconf`). So "nothing selected, nothing persisted, no default" resolves statically to the global config
    dir without checking the file system, and the min leaps shape (no config dirs, see `FT_59_95_81_63.tree_shape.md`)
    keeps creating nothing: `version_constraints` etc. land in `ref_root`, as before. Repos which relied on the implicit
    `gconf` must set the field explicitly (this repo already does). `_ConfConstPrimer.default_client_conf_dir_rel_path`
    stays only as a value for tests/helpers (see `TODO_32_41_01_30`).

**Implementation:** (PR C) moves the default out of `_BaseNode_state_selected_env_dir_rel_path` into the symlink node (see
`### Design`: `boot`/`read`/`reset`/`eval` variants; `read` = `op_start`/`op_shell`/`op_wrap`/lib).

### Design: one `Factory`, per-operation `Node`-s over a shared base

**Status:** DONE (applies to the `op_reset` and `op_eval` items below)

**Description:**
Instead of adding an `_ExecOperation` branch inside `_Node_state_local_conf_symlink_abs_path_inited`, split it the
way other states are already split by `_is_app` (e.g. `_Factory_state_reset_triggered`,
`_Factory_state_selected_env_dir_rel_path_inited`): a real `_NodeFactory` (replacing `@_trivial_factory`) picks
a `@_conditional_factory` `Node` class per `_ExecOperation`:

*   shared base `_BaseNode_state_local_conf_symlink_abs_path_inited`: everything common to all variants
    (resolve the symlink abs path from client conf; compute the expected symlink target relative to the symlink's own
    dir - today duplicated at `:3419-3425` and `:3441-3447`; create the symlink; the "not a symlink"/"not a dir"
    checks). The common pieces are factored into functions which are tested on their own, too.
*   read variant (`op_start`, `op_shell`, `op_wrap`, non-app entries): never creates the link, raises on a mismatch.
*   boot variant (`op_boot`): same, but creates the link if it is missing (today's behavior for `op_boot`).
*   reset variant (`op_reset`): same, but on a mismatch remove the link and re-create it. Everything other than a
    symlink-to-dir (a real file/dir) still raises - never delete those.
*   eval variant (`op_eval`): never reads/writes the symlink; uses the selected env dir
    (see `op_eval` decisions below).

The factory switches on `env_ctx._exec_operation`.

**Return value (per `## Path`):**
All variants return the **direct** abs path of the env config dir (`ref_root` + the symlink's value or, for `op_eval`,
the selected rel path) - never the symlink path itself. The symlink is only created/validated as a side effect.
Consumers which join file names onto the returned path (`state_local_conf_file_abs_path_inited`,
the `version_constraints` file in `state_reset_triggered`/`state_venv_driver_prepared`/
`state_version_constraints_generated`, ...) need no change of their own - they stop depending on the symlink
once the returned value does. Still to verify: `metaprimer`/`local_repo` users of this state and the tests of the
consumers above do not assume the returned value is a symlink.

**Notes:**
*   No new parent state: the choice is made by the factory, so the node does not depend on
    `state_input_exec_operation_loaded` (the existing tests keep working as is - they exercise the `read` variant).
*   Ordering: `env_ctx._exec_operation` is set as a side effect of evaluating `state_input_exec_operation_loaded`,
    and the factory runs when the symlink state is first requested. The order is ensured by the DAG (not by the
    factory evaluating states itself - no factory does): every state which depends on the symlink state also depends
    on `state_input_exec_operation_loaded`, listed before it. Under `_is_app` only
    (`FT_77_15_06_50.dynamic_DAG.md`: `func_start_app`/`func_call_lib` do not process the exec operation; there
    `_exec_operation` is `None` => the `read` variant): `state_local_conf_file_abs_path_inited` and
    `state_derived_conf_data_loaded` became `_is_app`/`_not_is_app` conditional factories for this.
    Guarded by `test_EnvState_exec_operation_precedes_symlink_in_parents`.
    Tests set `env_ctx._exec_operation` directly.

    `_trivial_factory`)
*   `src/protoprimer/main/protoprimer/primer_kernel.py:4238-4244` (`_Factory_state_reset_triggered`, the pattern to

### `op_eval` must not touch the persisted symlink at all

**Status:** DONE

**Description:**
Per the spec table, `op_eval`'s outcome on a mismatch is `override`, not `failure` - it must evaluate the
resolved value without reading, validating, or writing the persisted symlink. Today `op_eval` shares the exact
same `_Node_state_local_conf_symlink_abs_path_inited` path `op_boot` uses (confirmed empirically: `./prime eval
--env dst/test_python_med` raised the identical `AssertionError` `boot` would). This needs a real code change:
`op_eval` must evaluate the resolved env value independently of `state_local_conf_symlink_abs_path_inited`'s
read/compare/write, consistent with [FT_19_44_42_19.effective_config.md]'s "`eval` is read-only" intent. The
`persisted? no` row (`run`) implies this applies even when nothing is persisted yet - `eval` should never create
the symlink either.

**Decisions:**
*   `op_eval` ignores the persisted symlink entirely (regardless of whether `--env` is given): the values are loaded
    from the **selected** environment, without depending on the link being present (or matching).
    Downstream nodes read the env conf through the symlink path (`state_local_conf_file_abs_path_inited`
    -> `state_env_conf_file_data_loaded` -> all derived states), so for `op_eval` the node must provide the abs path
    of the selected env dir (`ref_root` + selected rel path) instead of the symlink path.
    Open consumer check: other nodes in `derived_data_env_states` (`venv`/`log`/`run`/`tmp`/`cache` dirs) which
    evaluate through this node during `eval`.
*   `op_eval` + nothing selected (`None`: no `--env` and no default env configured) - keep the current early return
    (`ref_root`, no symlink touched) for now. The code has a `TODO` referencing
    [TODO_41_10_50_01.implement_env_selector.md] asking why `None` is possible at all
    (repo config without env-specific config?).
