## Description

Today's CI (`test_py_min.yaml`, `test_py_med.yaml`, `test_py_max.yaml`) runs only on Linux (`ubuntu-22.04`), testing
`min`/`med`/`max` Python versions (see [FT_84_11_73_28.supported_python_versions.md]). `test_py_med_windows.yaml`
added a first experimental Windows job (Milestone 1 of [TODO_50_98_96_87.support_windows.md]), but only for `med`,
`continue-on-error: true`, bootstrap-only (no `pytest`).

Goal: build out a full CI test grid across all 3 target platforms (`linux`, `darwin`, `windows`), with this
coverage grid:

| Platform  | min | med | max |
|-----------|-----|-----|-----|
| `linux`   | yes | yes | yes |
| `darwin`  | --- | yes | yes |
| `windows` | --- | yes | yes |

(`min` (3.7) is deliberately only tested on `linux` - asymmetric by design, not an oversight: `darwin`/`windows`
only test `med`/`max`.)

CI jobs are assumed to split per-platform, each job testing its own set/sub-set of `min`/`med`/`max` - i.e. a
`windows`-targeted job only ever runs `{med, max}`, never `min`, rather than one job's matrix spanning all three
and skipping the invalid cell.

Workflow files are not required to be deduplicated across platforms (one `.yaml` per platform, or even per
`(platform, python-version)` cell, is fine) - if sharing steps across platforms (a matrix, a composite action, a
reusable workflow) would complicate the workflow, keep it platform-specific instead. Deduplication only matters
for the `pytest` test suite itself (see `## Plan` below), not for the CI workflow files that invoke it.

Once tests run across several jobs and platforms, their coverage has to be combined
(see [TODO_29_67_72_68.combine_coverage_across_jobs.md]).

### Replace `os.name` with a `sys.platform`-based `_TargetPlatform` enum

**Status:** TO_DECIDE

**Description:**
The kernel currently distinguishes only POSIX vs. Windows, via `_ConfConstGeneral.is_os_windows = os.name == "nt"`
(`primer_kernel.py:1350`, consumed again at `:5952` in `_switch_python`'s `os.execve`-vs-`subprocess.run` branch).
That binary check is enough for every platform branch that exists today, because `darwin` has always been lumped
in with the POSIX `else` arm and happened to behave correctly there. A 3-way CI grid (`linux`/`darwin`/`windows`)
doesn't strictly *require* a 3-way runtime enum yet - nothing found so far needs `darwin`-specific kernel behavior
distinct from `linux` - but this task asks for a `sys.platform`-based `_TargetPlatform` (`platform_linux` /
`platform_darwin` / `platform_windows`) plus a lookup function, as the forward-looking replacement for `os.name`,
so the enum is already in place if/when a real `darwin`-only branch is ever needed.

**References:**
*   `src/protoprimer/main/protoprimer/primer_kernel.py:1350` (`_ConfConstGeneral.is_os_windows`), `:5952`
    (`_switch_python`'s branch)
*   `src/proto_code/proto_kernel.py` - mirrors the same two lines (kept in sync with `primer_kernel.py`, per the
    file's own "GENERATED CONTENT" boilerplate header)
*   Python docs: `sys.platform` values - `"linux"`, `"darwin"`, `"win32"` (not `"windows"`)
*   [TODO_50_98_96_87.support_windows.md] "Path case-(in)sensitivity: NTFS vs. POSIX filesystems" - the one open
    item most likely to eventually need a real `darwin`-specific branch (APFS is case-insensitive by default, same
    concern as NTFS)

**Options:**
*   **A.** Introduce `_TargetPlatform`/`_get_target_platform()` now, and migrate `is_os_windows`'s two call sites
    to compare against `_TargetPlatform.platform_windows` instead of `os.name == "nt"`, even though no call site
    needs the 3-way split yet. Pros: one authoritative, testable mapping from `sys.platform`; sets the precedent of
    `sys.platform` over `os.name` project-wide, per this task's own ask; ready the moment a real `darwin`-specific
    need shows up. Cons: migrates two call sites with no present behavior change - pure refactor, needs its own
    test coverage to justify the churn.
*   **B.** Keep `is_os_windows`/`os.name == "nt"` in `primer_kernel.py` exactly as-is until a kernel call site
    actually needs to tell `darwin` apart from `linux`; define `_TargetPlatform` only in the CI/test-support code
    that drives the grid itself, not in the kernel. Pros: no churn on code with no behavioral need yet; consistent
    with the project's general reluctance to special-case without a confirmed need (same reasoning already used
    for not special-casing `HEAD` in `TODO_36_76_61_27.semver_backward_compatibility_testing.md`, referenced from
    [TODO_50_98_96_87.support_windows.md]). Cons: the enum this task explicitly asks for would live outside the
    kernel, and `is_os_windows` would keep using `os.name` after this task says to stop.

**Status:** TO_DECIDE

**Description:**
`dst/test_python_min`, `dst/test_python_med`, `dst/test_python_max` are env dirs (`proto_kernel.json` +
`version_constraints.txt`) exercised so far only on Linux. `test_py_med_windows.yaml` (Milestone 1 of
[TODO_50_98_96_87.support_windows.md]) reused `dst/test_python_med` as-is for Windows rather than creating its own
env, and that already produced one real divergence: `dst/test_python_med/version_constraints.txt` legitimately
differs on Windows (drops `secretstorage`/`jeepney`, adds `pywin32-ctypes`) - worked around by excluding that one
file from the CI job's "no local changes" diff check, not by giving Windows its own env. A full grid (up to 4 more
cells beyond today's 3: `med`/`max` x `darwin`/`windows`) will hit the same divergence on every cell, and a single
checked-in `version_constraints.txt` per version dir cannot represent more than one platform's resolved lock state
at once.

**References:**
*   `dst/test_python_med/proto_kernel.json`, `dst/test_python_med/version_constraints.txt`
*   `.github/workflows/test_py_med_windows.yaml` - the exclusion comment/step for `version_constraints.txt`
*   [TODO_41_10_50_01.implement_env_selector.md], [TODO_89_47_85_02.fix_selected_persistent_env_handling.md] - env-selection
    precedence work this overlaps with
*   `--env`/`_SyntaxArg.arg_env` (`primer_kernel.py:505`), consumed via `_ParsedArg.name_selected_env_dir`
    (`:3331-3339`) - the existing mechanism any new `dst/` dir would be selected through; no kernel change needed
    just to add a dir, only to decide its name/shape

**Options:**
*   **A.** One dir per `(python-version, platform)` cell, e.g. `dst/test_python_med_windows`,
    `dst/test_python_med_darwin`, alongside the unsuffixed Linux ones. Pros: explicit, grep-able, no kernel change;
    each dir's `version_constraints.txt` is simply whatever that platform/version resolves to, checked in normally
    with no exclusion hacks. Cons: dir count roughly doubles for `med`/`max`; `proto_kernel.json`'s
    `required_python_version`/`python_selector_file_rel_path` fields would be duplicated verbatim across e.g.
    `test_python_med` and `test_python_med_windows` (same Python version, same selector script - nothing actually
    platform-specific in that file today).
*   **B.** Keep the shared, unsuffixed dirs per version (as Milestone 1 already does), and keep working around
    `version_constraints.txt` divergence per-platform via the CI job's own diff-check exclusion, as already done
    for Windows. Pros: no new dirs. Cons: the exclusion list grows one entry per newly-diverging platform, and a
    shared `version_constraints.txt` stops meaning anything checked-in once more than one platform's CI job is
    allowed to silently disagree with it.
*   **C.** Keep `proto_kernel.json` shared/unsuffixed per version (confirmed platform-agnostic content today), but
    stop checking in `version_constraints.txt` at all if it is in fact a regenerable lock artifact rather than a
    hand-maintained one (needs confirming how/when it's produced) - removing the need for either new dirs or
    diff-check exclusions.
*   **D.** Delegate the choice to whichever mechanism [TODO_41_10_50_01.implement_env_selector.md] ends up
    implementing (an env-selector script, analogous to the existing `python`-selector scripts) - have the selector
    itself compute the platform-suffixed (or not) env dir, rather than hardcoding the dir name into each CI
    workflow's `--env` arg.

### Avoiding test-suite duplication across platforms

**Status:** TO_DECIDE

**Description:**
This is specifically about the `pytest` test suite's own content, not the CI workflow files that invoke it (those
may legitimately stay platform-specific - see `## Description` above). Already tracked in
[TODO_50_98_96_87.support_windows.md]'s "Test suite hardcodes POSIX path separators..." item (not a new problem),
a growing fraction of `pytest` tests hardcode POSIX-only expected values (literal `/`-joined paths) instead of
building them the same platform-aware way the production code does. Running the existing suite against a new
platform does not need *duplicate* test files per platform - the goal is the opposite: one shared test with a
platform-aware expectation, with only the genuinely-divergent assertions actually branching per platform (or
skipped where a feature plainly cannot exist on a platform, e.g. a POSIX-privilege-only symlink test on Windows).
Outright per-platform test duplication should stay the fallback for cases where sharing the test would complicate
it more than copying it, not the default.

**References:**
*   [TODO_50_98_96_87.support_windows.md] "Test suite hardcodes POSIX path separators and direct-exec assumptions
    pervasively" `## Plan` item, Option B there ("a small, shared test helper... usable across all affected
    sub-projects") - already proposed but not yet decided/implemented, and this item's natural home
*   The `_TargetPlatform` enum sub-section above - whatever it resolves to is the natural thing a
    platform-conditional test/marker would key off of

**Options:**
*   **A.** Rely entirely on [TODO_50_98_96_87.support_windows.md]'s own item (the shared `os.path.join`-based
    expected-value helper, its Option B) as the sole mechanism, and gate each new grid cell's `pytest` step on how
    much of the suite that helper has actually fixed so far - don't invent a second, competing deduplication
    strategy in this doc.
*   **B.** Additionally introduce a `pytest` marker/fixture keyed off `_TargetPlatform` (e.g.
    `@pytest.mark.skipif(_get_target_platform() != _TargetPlatform.platform_windows, reason=...)`) for the
    genuinely-impossible-elsewhere cases (e.g. the Windows symlink-privilege test), so "this test only makes sense
    on platform X" is declared once, declaratively, in the shared suite, instead of being omitted or duplicated
    into a separate platform-specific test file.
*   **C.** Allow plain duplication (a dedicated platform-specific test file, kept separate rather than folded into
    the shared suite with skip conditions) wherever sharing a test would complicate it more than copying it -
    the test-suite equivalent of the CI-workflow allowance in `## Description`: deduplication is a means, not an
    end in itself.
