## Description

CI runs a test job per grid cell (see the table below): `test_py_{min,med,max}_linux.yaml`, `test_py_{med,max}_darwin.yaml`
(full `pytest`) and `test_py_{med,max}_windows.yaml` (bootstrap plus selected portable tests: Milestone 1 of
[TODO_50_98_96_87.support_windows.md]), testing `min`/`med`/`max` Python versions (see
[FT_84_11_73_28.supported_python_versions.md]). No job is `continue-on-error` (the non-Linux ones were promoted, see "Promote grid jobs" below).

Each cell has its own env dir `dst/test_python_{min,med,max}_{platform}`, picked by the env selector
(`src/proto_code/env_selector.py`) from the GitHub job id `test_py_{min,med,max}_{platform}` (no `--env` in these jobs).
The `linux` and `darwin` workflows share their steps via the composite action `.github/actions/test_env_posix`, and the
`windows` ones via `.github/actions/test_env_windows` (PowerShell, selected portable tests only: its steps genuinely differ).
Composite steps run in the caller's job, so the job id the selector reads stays `test_py_{level}_{platform}`.

Goal: build out a full CI test grid across all 3 target platforms (`linux`, `darwin`, `windows`), with this
coverage grid:

| Platform  | min | med | max |
|-----------|-----|-----|-----|
| `linux`   | yes | yes | yes |
| `darwin`  | --- | yes | yes |
| `windows` | --- | yes | yes |

(`min` (3.7) is deliberately only tested on `linux` - asymmetric by design, not an oversight: `darwin`/`windows`
only test `med`/`max`.)

CI jobs are assumed to split per-platform, each job testing its own set/sub-set of `min`/`med`/`max` - i.e. a
`windows`-targeted job only ever runs `{med, max}`, never `min`, rather than one job's matrix spanning all three
and skipping the invalid cell.

Workflow files are not required to be deduplicated across platforms (one `.yaml` per platform, or even per
`(platform, python-version)` cell, is fine) - if sharing steps across platforms (a matrix, a composite action, a
reusable workflow) would complicate the workflow, keep it platform-specific instead. Deduplication only matters
for the `pytest` test suite itself (see `## Plan` below), not for the CI workflow files that invoke it.

Once tests run across several jobs and platforms, their coverage has to be combined
(see [TODO_29_67_72_68.combine_coverage_across_jobs.md]).

### Replace `os.name` with a `sys.platform`-based `_TargetPlatform` enum

**Status:** DONE

**Description:**
The kernel used to distinguish only POSIX vs. Windows, via `_ConfConstGeneral.is_os_windows = os.name == "nt"`
(consumed in the venv layout constants and in `_switch_python`'s `os.execve`-vs-`subprocess.run` branch). That binary
check was enough for every platform branch, because `darwin` has always been lumped in with the POSIX `else` arm and
behaved correctly there. A 3-way CI grid (`linux`/`darwin`/`windows`) does not strictly *require* a 3-way runtime enum -
nothing found so far needs `darwin`-specific kernel behavior distinct from `linux` - but this task asks for a
`sys.platform`-based `_TargetPlatform` plus a lookup function, as the forward-looking replacement for `os.name`, so the
enum is already in place if/when a real platform-specific branch is needed.

**References:**
*   `src/protoprimer/main/protoprimer/primer_kernel.py`: `_ConfConstGeneral.is_os_windows` and `_switch_python`'s branch
*   `src/proto_code/proto_kernel.py` - mirrors the same two lines (kept in sync with `primer_kernel.py`, per the
    file's own "GENERATED CONTENT" boilerplate header)
*   Python docs: `sys.platform` values - `"linux"`, `"darwin"`, `"win32"` (not `"windows"`)
*   [TODO_50_98_96_87.support_windows.md] "Path case-(in)sensitivity: NTFS vs. POSIX filesystems" - the one open
    item most likely to eventually need a real `darwin`-specific branch (APFS is case-insensitive by default, same
    concern as NTFS)

**Options:**
*   **A.** Introduce `_TargetPlatform`/`_get_target_platform()` now, and migrate `is_os_windows`'s two call sites
    to compare against `_TargetPlatform.platform_windows` instead of `os.name == "nt"`, even though no call site
    needs the 3-way split yet. Pros: one authoritative, testable mapping from `sys.platform`; sets the precedent of
    `sys.platform` over `os.name` project-wide, per this task's own ask; ready the moment a real `darwin`-specific
    need shows up. Cons: migrates two call sites with no present behavior change - pure refactor, needs its own
    test coverage to justify the churn.
*   **B.** Keep `is_os_windows`/`os.name == "nt"` in `primer_kernel.py` exactly as-is until a kernel call site
    actually needs to tell `darwin` apart from `linux`; define `_TargetPlatform` only in the CI/test-support code
    that drives the grid itself, not in the kernel. Pros: no churn on code with no behavioral need yet; consistent
    with the project's general reluctance to special-case without a confirmed need (same reasoning already used
    for not special-casing `HEAD` in `TODO_36_76_61_27.semver_backward_compatibility_testing.md`, referenced from
    [TODO_50_98_96_87.support_windows.md]). Cons: the enum this task explicitly asks for would live outside the
    kernel, and `is_os_windows` would keep using `os.name` after this task says to stop.

**Implementation:** Option A. `_TargetPlatform` (`linux`, `darwin`, `freebsd`, `windows`, with `is_posix()`) and
`_get_target_platform()` are added to `primer_kernel.py` (mirrored in `proto_kernel.py`).
`_ConfConstGeneral.is_os_windows` stays (clearer for `.exe`/`.bat` naming: not POSIX does not necessarily mean Windows)
but is now `_get_target_platform() == _TargetPlatform.platform_windows`; `_switch_python` reads it unchanged.
An unrecognized `sys.platform` raises `ValueError`. `freebsd` has no CI cell (uv supports it at Tier 3 only), so it is
expected to work, not tested.

### Separate target envs per platform under `dst/`

**Status:** DONE

**Description:**
`dst/test_python_{min,med,max}_linux` are env dirs (`proto_kernel.json` + `version_constraints.txt`).
`test_py_med_windows.yaml` (Milestone 1 of [TODO_50_98_96_87.support_windows.md]) first reused
`dst/test_python_med_linux` as-is for Windows rather than creating its own env, and that produced one real divergence:
`dst/test_python_med_linux/version_constraints.txt` legitimately differs on Windows (drops `secretstorage`/`jeepney`,
adds `pywin32-ctypes`) - worked around by excluding that one file from the CI job's "no local changes" diff check, not
by giving Windows its own env. Every other non-Linux cell (`med`/`max` x `darwin`/`windows`) hits the same divergence,
and a single checked-in `version_constraints.txt` per version dir cannot represent more than one platform's resolved
lock state at once.

**References:**
*   `dst/test_python_med_linux/proto_kernel.json`, `dst/test_python_med_linux/version_constraints.txt`
*   `.github/workflows/test_py_med_windows.yaml` - the job which used to exclude `version_constraints.txt` from the check
*   `src/proto_code/env_selector.py` - maps the job id (or, with `CI=true`, the host `python` and platform) to the env dir
*   [FT_03_31_63_70.environment_selection.md] - env-selection precedence this overlaps with
*   `--env`/`_SyntaxArg.arg_env` - the explicit way to select any `dst/` dir (it wins over the selector)

**Options:**
*   **A.** One dir per `(python-version, platform)` cell, e.g. `dst/test_python_med_windows`,
    `dst/test_python_med_darwin`, alongside the `_linux` ones. Pros: explicit, grep-able, no kernel change;
    each dir's `version_constraints.txt` is simply whatever that platform/version resolves to, checked in normally
    with no exclusion hacks. Cons: dir count roughly doubles for `med`/`max`; `proto_kernel.json`'s
    `required_python_version`/`python_selector_file_rel_path` fields would be duplicated verbatim across e.g.
    `test_python_med_linux` and `test_python_med_windows` (same Python version, same selector script - nothing actually
    platform-specific in that file today).
*   **B.** Keep the shared dirs per version (without a platform suffix) (as Milestone 1 already does), and keep working around
    `version_constraints.txt` divergence per-platform via the CI job's own diff-check exclusion, as already done
    for Windows. Pros: no new dirs. Cons: the exclusion list grows one entry per newly-diverging platform, and a
    shared `version_constraints.txt` stops meaning anything checked-in once more than one platform's CI job is
    allowed to silently disagree with it.
*   **C.** Keep `proto_kernel.json` shared/unsuffixed per version (confirmed platform-agnostic content today), but
    stop checking in `version_constraints.txt` at all if it is in fact a regenerable lock artifact rather than a
    hand-maintained one (needs confirming how/when it's produced) - removing the need for either new dirs or
    diff-check exclusions.
*   **D.** Delegate the choice to the env selector ([FT_03_31_63_70.environment_selection.md])
    (an env-selector script, analogous to the existing `python`-selector scripts) - have the selector
    itself compute the platform-suffixed (or not) env dir, rather than hardcoding the dir name into each CI
    workflow's `--env` arg.

**Implementation:** Options A and D: every non-Linux cell has its own dir, `dst/test_python_{med,max}_{darwin,windows}`
(with its own `version_constraints.txt`), and the env selector computes the platform-suffixed dir name instead of each
workflow's `--env` arg. The `max` cells are copies of the `med` ones for `3.15` (`proto_kernel.json`). A new cell's
`version_constraints.txt` is generated by its first run and then committed (it differs per platform). Options B and C
are not used.

### Avoiding test-suite duplication across platforms

**Status:** DONE

**Description:**
This is specifically about the `pytest` test suite's own content, not the CI workflow files that invoke it (those
may legitimately stay platform-specific - see `## Description` above). Already tracked in
[TODO_50_98_96_87.support_windows.md]'s "Test suite hardcodes POSIX path separators..." item (not a new problem),
a growing fraction of `pytest` tests hardcode POSIX-only expected values (literal `/`-joined paths) instead of
building them the same platform-aware way the production code does. Running the existing suite against a new
platform does not need *duplicate* test files per platform - the goal is the opposite: one shared test with a
platform-aware expectation, with only the genuinely-divergent assertions actually branching per platform (or
skipped where a feature plainly cannot exist on a platform, e.g. a POSIX-privilege-only symlink test on Windows).
Outright per-platform test duplication should stay the fallback for cases where sharing the test would complicate
it more than copying it, not the default.

**References:**
*   [TODO_50_98_96_87.support_windows.md] "Test suite hardcodes POSIX path separators and direct-exec assumptions
    pervasively" `## Plan` item, Option B there ("a small, shared test helper... usable across all affected
    sub-projects") - already proposed but not yet decided/implemented, and this item's natural home
*   The `_TargetPlatform` enum sub-section above - whatever it resolves to is the natural thing a
    platform-conditional test/marker would key off of

**Options:**
*   **A.** Rely entirely on [TODO_50_98_96_87.support_windows.md]'s own item (the shared `os.path.join`-based
    expected-value helper, its Option B) as the sole mechanism, and gate each new grid cell's `pytest` step on how
    much of the suite that helper has actually fixed so far - don't invent a second, competing deduplication
    strategy in this doc.
*   **B.** Additionally introduce a `pytest` marker/fixture keyed off `_TargetPlatform` (e.g.
    `@pytest.mark.skipif(_get_target_platform() != _TargetPlatform.platform_windows, reason=...)`) for the
    genuinely-impossible-elsewhere cases (e.g. the Windows symlink-privilege test), so "this test only makes sense
    on platform X" is declared once, declaratively, in the shared suite, instead of being omitted or duplicated
    into a separate platform-specific test file.
*   **C.** Allow plain duplication (a dedicated platform-specific test file, kept separate rather than folded into
    the shared suite with skip conditions) wherever sharing a test would complicate it more than copying it -
    the test-suite equivalent of the CI-workflow allowance in `## Description`: deduplication is a means, not an
    end in itself.

**Implementation:** Option B (markers) is implemented: `requires_posix` / `requires_windows` in
`local_test.case_condition` (keyed off `_get_target_platform().is_posix()`). Used by the platform-constants test
(`test_platform_constants.py`, hard-coded expected values per platform), the `execve`-based `_switch_python`, shell and
wrap tests, while Windows-only branches (`subprocess.run` in `_switch_python`, the shell guard) are tested on any
platform by patching. Option A (the shared path-building helper) stays tracked in
[TODO_50_98_96_87.support_windows.md]'s separators item; Option C is not used.

### First `darwin` CI job

**Status:** DONE

**Description:**
There was no macOS CI (`darwin` was only "actively run" by a developer locally, per
[TODO_50_98_96_87.support_windows.md]'s `## Description`). Unlike Windows, `darwin` is a real POSIX OS: `os.execve`, the

    calls out APFS as "not purely Windows-only"
*   `.github/workflows/test_py_med_linux.yaml` (full bootstrap + `pytest`, the optimistic template) vs.
    `test_py_med_windows.yaml` (the Milestone 1 template: bootstrap-only at the time, the cautious one)
*   GitHub-hosted `macos-latest` runner (currently `macos-14`, Apple Silicon/`arm64`, since GitHub's 2024 default
    change)

**Options:**
*   **A.** Model the first `darwin` job directly on `test_py_med_linux.yaml` (full `pytest` run included from the
    start), since nothing concrete suggests macOS needs Windows' workarounds - optimistic, but could surface a
    real failure on the very first run, same as Windows Milestone 1's first few runs did.
*   **B.** Be conservative and mirror Windows Milestone 1's own methodology exactly: a bootstrap-only,

    matches the already-proven "milestone, not final design" approach.

**Implementation:** Option A. `test_py_med_darwin.yaml` (`macos-latest`, full `pytest`) is modeled on
`test_py_med_linux.yaml`, (it was `continue-on-error` at first). The env selector maps
`darwin` to `dst/test_python_med_darwin`; each `dst/test_python_{med,max}_darwin/version_constraints.txt` was generated
by the first run and committed (without `secretstorage`/`jeepney`, as on `windows`).
Confirmed by CI: both `darwin` cells are green with the full `pytest` (1844 passed, 105 skipped; ~8.5 min for `max`,
~12.5 min for `med`) - no macOS-specific kernel change or test fix was needed (so far no sign of the APFS
case-sensitivity concern).
