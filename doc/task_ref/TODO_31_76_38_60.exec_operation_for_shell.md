`ExecOperation.command_shell` (`shell` sub-command) is implemented:
*   uses `-c`/`--command`, like any shell does, for a single non-interactive command.
*   piping a script to `stdin` (with no `-c`) already works too - e.g. `echo 'some script' | proto_code shell` -
    but only as a side effect of the underlying shell's own interactive/`stdin` handling
    (`ShellDriverZsh` adds `-s` when `stdin` is not a tty; `bash` reads piped `stdin` the same way in `-i` mode).
    There is no dedicated `ExecOperation.run_mode`/`shell_mode` flag or explicit "pipe mode" - it is not a
    deliberately declared feature of `primer_kernel.py`, just inherited shell behavior.
*   `venv_shell` (`metaprimer/cmd_venv_shell.py`) is deprecated in favor of it (prints a deprecation warning).

Remaining open questions:

*   Do we want a declared `ExecOperation.run_mode`/`shell_mode` instead of relying on this implicit behavior -
    e.g. to make the contract explicit, or to support cases the implicit shell behavior does not cover?

    See [pipe_to_execute_with_activated_venv][UC_36_72_11_12.pipe_to_execute_with_activated_venv.md].

*   Given piping already works, can `venv_shell` be removed entirely (not just deprecated)?
