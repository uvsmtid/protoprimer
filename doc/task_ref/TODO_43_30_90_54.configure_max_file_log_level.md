Make the file log level limit configurable in the config file (instead of the hardcoded `logging.INFO`).

## Why

*   Per [log_verbosity][FT_38_73_38_52.log_verbosity.md], the file log level defaults to `logging.INFO`
    and is adjusted to be at least as verbose as `stderr` (when `stderr` is more verbose, e.g. with `-v`).

*   In the code (the file log handler setup) this is:
    `file_log_level = logging.INFO`, then lowered to the `stderr` handler level if that is lower.
    So `logging.INFO` is the hard maximum of the file log level (the highest numeric value, the fewest entries) -
    "MAX" in the in-place TODO (NOTE: the higher the level, the fewer the log entries).

*   There is no way to set it other than changing `stderr` verbosity:
    a user cannot, for example, always keep a `DEBUG` file log while keeping `stderr` quiet,
    or reduce the file log to `WARN` to save space.

## What to do

*   Add a config field for the max file log level (a name as in `LogLevel`, or an `int`),
    resolved like other config values (`_get_overridden_value_or_default`) with the default `logging.INFO`.

*   Evaluate it before the file log handler is configured:
    the file log starts only after its config is resolved (the log file itself says so in its first lines),
    so the field must not require anything evaluated later.

*   Keep the rule "at least as verbose as `stderr`" and update [log_verbosity][FT_38_73_38_52.log_verbosity.md].

*   Add the new field to the config docs and to the `metaprimer` renderer (fields descriptions are rendered from there).

## Considerations

*   Pros: a user controls the file log independently of `stderr`.

*   Cons / risks: a new `ConfField` is a new config contract (it touches the `metaprimer` renderer and its tests);
    interplay of the new field with `-q`/`-v` must be explicit in the docs.
