## Description

`protoprimer` aims to be cross-platform, but today it only runs (and is only tested) on `*nix` (actively run on Linux and macOS).
The GitHub issue above lists the known rough edges informally; this doc tracks each of them (confirmed or only suspected)
as its own item in `## Plan` below, so each can be confirmed, decided, and fixed independently, across however many PRs it takes.

A design question recurs across several items below: should a fix preserve **identical** behavior on every platform,
or is it acceptable (even preferable) to branch per `os.name`/`sys.platform`?

The clearest example is process replacement:

*   `_switch_python` and `_ShellDriverBase.run_shell` both call `os.execve` to replace the current process image
    with a new `python`/shell process, carrying over `argv`/`env`. This is how the kernel "hands off" between
    bootstrap stages (see [FT_72_45_12_06.python_executable.md][FT_72_45_12_06.python_executable.md]) and how
    `op_shell` launches an interactive shell.
*   Windows has no POSIX `exec()`; CPython's `os.execve` on Windows is emulated (spawn + wait + `_exit`) rather
    than a true in-place replacement.

Options considered for this (and similarly-shaped) cases:

*   **A. Keep one code path, rely on CPython's Windows emulation of `os.execve`.**
    Pros: no branching, nothing new to maintain; consistent with the project generally avoiding special-casing a
    single environment (e.g. no special-casing of the `HEAD` baseline in
    `doc/task_ref/TODO_36_76_61_27.semver_backward_compatibility_testing.md`).
    Cons: the emulation is a spawn+wait+exit chain under the hood, not a real replacement — subtleties (exit-code
    propagation, console/job-object handling, open handles, interaction with `venv` activation) are unconfirmed on
    Windows and have never been exercised by CI.

*   **B. Branch per-platform: POSIX keeps `os.execve`; Windows uses an explicit `subprocess.run(...)` followed by
    `sys.exit(returncode)` chain of children.**
    Pros: explicit and inspectable; matches what the GitHub issue itself proposes; avoids depending on undocumented
    CPython-on-Windows emulation behavior.
    Cons: adds a permanent platform branch (or a small driver abstraction) in a part of the kernel that is otherwise
    platform-agnostic; adds one extra process layer in the chain on Windows only; needs its own tests.

This doc does not resolve that question globally — each sub-section in `## Plan` makes its own
Status/Options/Implementation call for its own piece of code, since the trade-off differs per call site (e.g. the
`python` hand-off in `_switch_python` vs. the interactive `shell` hand-off in `_ShellDriverBase.run_shell` have
different blast radii).

### Process replacement: `os.execve` on Windows

**Status:** TO_FIX (confirmed for `_switch_python`; `_ShellDriverBase.run_shell` not exercised by Milestone 1, still TO_CONFIRM)

**Description:**
Two call sites replace the current process via `os.execve`:
*   `_switch_python` — hands off from the bootstrap `python` to the next required `python` across `_StateStride`
    transitions, passing `exec_argv`/`required_environ`.
*   `_ShellDriverBase.run_shell` — replaces the current process with the interactive/`-c` shell (`bash`/`zsh`/`sh`),
    after writing an init file.

Windows has no POSIX `exec()`; CPython emulates `os.execve` there via spawn + wait + `_exit`, which is not a drop-in
replacement (handle inheritance, console/job-object behavior, and exit-code semantics differ from a true replace).

**References:**
*   `src/protoprimer/main/protoprimer/primer_kernel.py:5932` (`_switch_python`)
*   `src/protoprimer/main/protoprimer/primer_kernel.py:1181` (`_ShellDriverBase.run_shell`)
*   [FT_72_45_12_06.python_executable.md][FT_72_45_12_06.python_executable.md] — documents the `python`-switch
    hand-off and already carries this exact TODO as an inline comment.
*   [FT_64_09_03_66.invoke_condition.md][FT_64_09_03_66.invoke_condition.md] → `### TODO: host_not_posix` — already
    lists this as the primary blocker for the `host_not_posix` invoke condition.
*   GitHub issue #40: "Instead of using `os.execv` (which does not create new process), Windows has to use child
    processes (via `subprocess.run`)."
*   Python docs for `os.execve`: listed as "Availability: Unix, Windows", but Windows semantics are emulated, not
    native.

**Options:**
*   **A.** Keep `os.execve` uniformly, rely on CPython's Windows emulation. See trade-off in `## Description`.
*   **B.** Branch: POSIX keeps `os.execve`; Windows uses `subprocess.run(...)` + `sys.exit(completed.returncode)`.
    See trade-off in `## Description`.

**Implementation:**
*   Option B, for `_switch_python` only. CI evidence (PR #193, `test_py_med_windows`): a same-path self-reinvocation
    through `os.execve` on `windows-latest` produced no further log output at all after the "switching..." message
    and the job step failed with no visible Python traceback — consistent with Windows' spawn+wait+exit emulation
    losing this nested self-respawn's output/outcome. Branched `_switch_python` on `os.name == "nt"` to use
    `subprocess.run(exec_argv, env=required_environ)` followed by `sys.exit(completed_process.returncode)` instead;
    POSIX keeps `os.execve` unchanged. `_ShellDriverBase.run_shell`'s `os.execve` is untouched (not exercised by
    this bootstrap path) — still open, tracked as its own `TO_CONFIRM`.

### Entry script: `chmod +x` and the shebang line are POSIX-only concepts

**Status:** TO_CONFIRM

**Description:**
After generating/merging the entry script (`UC_71_59_90_97.generated_entry_script.md`), the kernel does
`os.chmod(path, st_mode | stat.S_IXUSR)` and the generated content starts with `#!/usr/bin/env python3`. On
Windows, `os.chmod` with POSIX permission bits is accepted but is effectively a no-op (NTFS has no POSIX execute
bit), and a shebang line is ignored by `cmd.exe`/PowerShell — but *is* parsed by the `py` launcher (`py.exe`) when
it is associated with `.py` files, so direct invocation (`./prime`) may or may not work on Windows depending on
how `py`/file associations are installed, rather than failing outright.

**References:**
*   `src/protoprimer/main/protoprimer/primer_kernel.py:2956-2960` (`os.chmod(... stat.S_IXUSR)`)
*   `src/protoprimer/main/protoprimer/primer_kernel.py:6492` (shebang line in `_generate_entry_script_content`)
*   `UC_71_59_90_97.generated_entry_script.md` (the use case this backs)
*   `py` launcher shebang handling: https://docs.python.org/3/using/windows.html#shebang-lines

**Options:**
*   **A.** No code change; document that on Windows the entry script must be invoked as `python ./prime` (or via
    the `py` launcher) rather than `./prime` directly, and that `chmod` is a harmless no-op there.
*   **B.** Additionally generate a `.cmd`/`.bat` wrapper alongside the `.py` entry script, for direct
    double-click/no-`python`-prefix invocation on Windows.

### `os.symlink` for the local-conf symlink: privilege and `target_is_directory`

**Status:** TO_FIX

**Description:**
`_Node_state_local_conf_symlink_abs_path_inited` creates the local-env symlink with `os.symlink(target, link)` and
no `target_is_directory` argument. On POSIX this is irrelevant (symlinks aren't typed). On Windows, `os.symlink`'s
third argument controls whether a *file* or *directory* symlink is created; omitting it (default `False`) can
create the wrong symlink type for a directory target. Separately, creating any symlink on Windows requires either
Administrator privileges or Developer Mode enabled — `protoprimer`'s bootstrap would simply fail with an
`OSError`/`PermissionError` without that, which is not mentioned anywhere in the kernel or its error messages.

**References:**
*   `src/protoprimer/main/protoprimer/primer_kernel.py:3424-3432`
*   `FT_92_51_35_07.local_env_link.md` (feature this implements)
*   Python docs: `os.symlink(src, dst, target_is_directory=False)` — "target_is_directory ... ignored on
    non-Windows platforms"
*   Windows symlink privilege requirement: `SeCreateSymbolicLinkPrivilege` / Developer Mode (Windows 10+)

**Options:**
*   **A.** Pass `target_is_directory=True` explicitly (the local-env target is always a directory) — safe on
    POSIX (the argument is ignored there) and correct on Windows.
*   **B.** Additionally detect the Windows privilege failure and raise a clearer error pointing at Developer Mode,
    instead of surfacing a bare `OSError`.

        `python` fallback basename should still resolve via `shutil.which` on Windows; to be confirmed.
    *   "Process replacement: `os.execve` on Windows" — possibly **not** blocking if CPython's Windows emulation
        of `os.execve` is good enough end-to-end; this experiment is exactly what would surface that either way.
