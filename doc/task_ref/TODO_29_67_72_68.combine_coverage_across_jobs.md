Combine test coverage across all GitHub Actions jobs (not just one `linux` job).

## Why

*   Only `cover.yaml` (`report_coverage`) measures and reports coverage:
    *   it runs on `ubuntu-latest` with `python` 3.15 only;
    *   it uploads to `coveralls.io` (`coverallsapp/github-action@v2`).

*   All other test jobs run tests but report no coverage:
    *   `test_py_min_linux.yaml` (`python` 3.7), `test_py_med_linux.yaml` (3.11), `test_py_max_linux.yaml` (3.15);
    *   `test_py_med_windows.yaml` (3.11 on Windows);
    *   `test_contract_compatibility.yaml` (old tests on new changes, old entry on new proto, ...);
    *   `test_invoke_condition.yaml` (scenarios in containers).

*   So the code which only runs elsewhere looks "uncovered":
    *   Windows-specific branches (`_ConfConstGeneral.is_os_windows`, `subprocess.run` instead of `os.execve`
        in `_switch_python`, `target_is_directory` for `os.symlink`, ...);
    *   `python`-version-specific branches (3.7 compatibility);
    *   scenarios which run in containers (`test_invoke_condition`) or in the baseline worktree (contract tests).

*   `coveralls.io` fails the check on any decrease (observed on PR #194: `coverage/coveralls` -
    "Coverage decreased (-0.05%) to 92.725%"), so partial coverage creates noise.

## Done

*   Combining approach: `coveralls.io` parallel builds.
    *   Every test workflow (`test_py_*`, `test_contract_compatibility`, `test_invoke_condition`) uploads its own `lcov` report
        (`coverallsapp/github-action@v2` with `parallel: true` and `flag-name: <job>`).
    *   The jobs are in separate workflow files: `needs:` cannot link them and `github.run_id` differs,
        so all of them pass the same `build-number: <commit sha>` to end up in one `coveralls.io` build.
    *   The build is closed by `.github/workflows/cover_finish.yaml` (`parallel-finished: true`):
        it is a `push` workflow (`workflow_run` only fires from the default branch, so it would not work on a feature branch),
        and its job waits via `cmd/wait_for_workflow_runs` until every test workflow has completed runs for the commit.
*   Data is combinable across OS-es and `python` versions:
    *   `gconf/coveragerc.ini` has `relative_files = true` and a `[paths]` section (absolute paths of containers
        and worktrees are rewritten to `src/`);
    *   `coverage` of the min job (`python` 3.7, `coverage==7.2.7`) uploads and merges fine with the newer ones.
*   Removed `.github/workflows/cover.yaml`: it stopped uploading and only duplicated a `test_py_*` job
    with a partial `fail_under` check.
*   `cmd/report_coverage` runs tests under `coverage` for all jobs (`--all_tests`, `--tests_file`, `--lcov_file`):
    one `python` command instead of `bash` and `pwsh` steps.
*   Code which runs in other places is measured (opt-in with `PROTOPRIMER_COVERAGE_DIR`):
    *   baseline worktree of `test_contract_compatibility` (`local_contract_compatibility.run_mode_tests`);
    *   containers of `test_invoke_condition` (`local_test.invoke_condition_helper`): a `sitecustomize.py` hook is installed
        into the stdlib of `python`-s by `local_test.container_hook_installer` (`PYTHONPATH` does not work:
        `./prime` runs `python` with `-I`), and the data is read from a mounted dir.
*   Result (PR #207): the combined number is 95.18% (3104 of 3244 lines), +2.1 over the previous build of `main`.

## Open

*   Decide how the check gates PR-s: `.github/workflows/cover.yaml` (the partial `fail_under = 80` check) is removed,
    so only the `coveralls.io` "decrease" rule gates now (`fail_under` in `gconf/coveragerc.ini` is only used
    by a local `cmd/report_coverage` run).
*   Confirm whether subprocesses started by `test_slow_integrated` are measured (not checked).
*   `os.execve` drops the data of the process which replaces itself (`_switch_python`):
    only the last `python` process of a chain saves its data - the invoke scenarios are under-measured
    (in the last run, 11 of 41 data files had any data, the other 30 were empty).
*   `cover_finish.yaml` keeps a runner busy (about 13 minutes per `push`) while it waits for the other workflows.
*   The wait only counts completed workflows, not successful uploads: a failed job uploads nothing,
    the flag is missing and the combined number drops (intended).
*   The list of workflows is repeated (`on` and arguments of `cmd/wait_for_workflow_runs` in `cover_finish.yaml`):
    adding a test workflow with an upload requires adding it there.
