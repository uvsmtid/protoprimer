`ExecOperation.op_start` (`start` sub-command) does not propagate any CLI args to
`ParsedArg.name_main_func`'s target function - it always presents it with a `sys.argv`
truncated to just the program name (see `Bootstrapper_state_start_executed`).

This is inconsistent with [start_app][FT_05_08_64_67.start_app.md]: an `entry_script`
is a genuinely separate process, so whatever the user types after the `entry_script` name
(e.g. `./cmd/some_app --foo bar`) naturally reaches the target function via `sys.argv` -
no explicit propagation code is even needed there.

`op_start` runs the target function in the *same* process/argv as
`proto_kernel.py start <main_func>` itself, so before this was fixed, `sys.argv` leaked
protoprimer's own `start`/`main_func` tokens into the target (breaking any target that
parses `sys.argv` on its own, e.g. `click`/`argparse` CLIs). The fix truncated to just
`sys.argv[:1]`, which correctly removes the leaked tokens, but also removes the ability
to pass any of the user's own args through - a regression relative to what `start_app`
already supports "for free".

Fix (implemented):
*   `parse_args` splits `remaining_argv` on the first literal `--` *before* either
    `argparse` pass runs: everything before it is parsed as usual (unchanged grammar,
    `main_func` stays a plain positional - no `argparse.REMAINDER`); everything after it
    is captured verbatim as `ParsedArg.name_target_args` and never shown to `argparse`
    at all.
*   In `Bootstrapper_state_start_executed`, `sys.argv` is rebuilt as
    `[sys.argv[0]] + target_args` instead of `sys.argv[:1]`.
*   If `target_args` is non-empty but the resolved `exec_operation` isn't
    `ExecOperation.op_start` (e.g. a stray `--` placed before the sub-command, or used
    with `boot`/`shell`/etc.), `parse_args` raises `ValueError` instead of silently
    discarding the tokens.

An earlier draft of this fix considered giving the `start` sub-command's parser a
trailing `nargs=argparse.REMAINDER` capture (after `main_func`) instead. That was
rejected:
*   `REMAINDER` grabs *everything* after `main_func`, including tokens that look like
    protoprimer's own flags - e.g. `start m:f -v` would silently stop setting
    protoprimer's own verbosity and instead pass `-v` to the target, a visible behaviour
    change for an existing, unrelated-looking command line.
*   The explicit `--` split removes that ambiguity entirely: with no `--`, behaviour is
    unchanged from before this fix (including `start m:f -v` still setting protoprimer's
    verbosity); only tokens after an explicit `--` are ever treated as target args.
*   `argparse`'s own handling of a literal `--` combined with `REMAINDER` has had
    cross-Python-version inconsistencies; doing the split manually (`list.index("--")`
    plus slicing) before `argparse` ever runs sidesteps that entirely.

This also resolved the fragility noted in the comment that used to sit above
`sys.argv = sys.argv[:1]`: that line assumed `start`'s grammar has no pass-through args,
which stopped being true once this was implemented.

Recursion through `op_start` chains:
Since `main_func` can name *any* importable function, it can also name `proto_main` itself
(`protoprimer.primer_kernel:proto_main`) - an ordinary function with nothing `op_start`-specific
about it. `proto_main` re-parses whatever `sys.argv` it is handed exactly like running
`proto_kernel.py` directly (it is what `proto_kernel.py` runs under `if __name__ == "__main__"`),
so handing it `[sys.argv[0]] + target_args` lets `target_args` itself be a full
`start <next_main_func> -- ...` command line. Chaining
`start protoprimer.primer_kernel:proto_main -- start <next> -- ...` therefore recurses one more
level per `--`, each link unwrapping exactly one level regardless of chain depth or how many
args follow the final `--` - see
`test_instant_scenario_start_recurses_through_proto_main` in `test_instant_scenario.py`.
