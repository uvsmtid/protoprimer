## Background

### Goal

Automatically detect backward-incompatible changes, so that a failing compatibility test means:
"this change requires a `major` version increment (or must be reverted/adjusted)".

### What is special about `protoprimer`

`protoprimer` is not a plain library: it bootstraps an environment through a hosted script.

*   [proto_kernel.py][FT_87_17_49_36.proto_kernel.md] is a copy of `protoprimer.primer_kernel`
    committed into the client repo (see [runtime][runtime.md]).
    It is pinned to whatever version was copied, and it is **not** updated with the `protoprimer` package.

*   `proto_kernel.py` starts working **before** `venv` exists.
    Once `venv` is created and `protoprimer` is installed there,
    `protoprimer.primer_kernel` from `venv` takes over
    (see [primer_runtime][FT_14_52_73_23.primer_runtime.md]).

*   Therefore, at any moment, two *different versions* of the same code base may cooperate within one bootstrap sequence:
    an old `proto_kernel.py` and a new (or old) `protoprimer.primer_kernel`.

Consequence: compatibility must be verified in two independent dimensions
(the second one is specific to `protoprimer`):
*   public interface compatibility,
*   bootstrap handoff compatibility.

### Kinds of compatibility

1.  **Public interface** compatibility (the classical `semver` case, see [backward_compatibility][FT_78_72_23_04.backward_compatibility.md]).
    Parts of the interface under test:

    *   API: public entries in `protoprimer.primer_kernel`
    *   CLI: args handled by `parse_args` (see `EnvState.state_args_parsed`, [CLI_compatibility][FT_62_88_55_10.CLI_compatibility.md])
    *   config schema: config files (e.g. `lconf`, `gconf`)
    *   env vars: `EnvVar` (see [env_var][FT_08_92_69_92.env_var.md]) - used by users **and** to propagate info across processes during bootstrap

2.  **Bootstrap handoff** compatibility:
    existing `proto_kernel.py` (old copy) vs `protoprimer.primer_kernel` from `venv` (new code).
    Parts of the interface under test:

    *   the data exchanged during the bootstrap sequence: CLI args, env vars, files/dirs (e.g. `venv`, `cache`, config), exit codes
    *   the `switch`/re-exec sequence from `proto_kernel.py` into `venv` (see [boot_vs_start][FT_58_74_37_70.boot_vs_start.md], [entry_script][FT_75_87_82_46.entry_script.md])

    `venv` is **not** a prerequisite of this testing: `proto_kernel.py` works before `venv` exists,
    so the old script can be tested against new code both with and without a pre-created `venv`.

    The same applies to an **old entry script** (generated by a baseline ref and committed in a client repo):
    it calls `proto_kernel.py` and must keep working with the new code (see the handoff categories below).

### Handoff test categories (decided)

*   **old proto vs new venv** (not synced):
    can an old `proto_kernel.py` bootstrap into the new `protoprimer` (with its new `protoprimer.primer_kernel`)?
    `proto_kernel.py` and `protoprimer.primer_kernel` are copies only when synced;
    while they are not synced yet (or a client repo keeps an old copy), they must remain interoperable.

*   **new proto + new venv** (synced):
    new `proto_kernel.py` (outside `venv`) and new `protoprimer.primer_kernel` are tested against the public interfaces.

*   **old entry script vs new proto and venv**:
    an entry script generated by a baseline ref keeps working with the new code.

### Baseline refs configuration (decided)

The baseline is any commit-ish string (branch name, tag name, commit id, etc.).
It is configured in the `pyproject.toml` of each releasable project under test
(`src/protoprimer/pyproject.toml` and `src/metaprimer/pyproject.toml`)
in a tool-specific table (PEP 518 reserves `[tool.*]` for this), for example:

```toml
[tool.local_contract_test]
baseline_refs = [
    "protoprimer-v0.9.0.final",
]
```

*   Each project has its own list: they are released separately and their tags have different prefixes.
*   The config is read from the current tree (new code), not from the baseline ref.
*   CI must fetch the refs (full clone with tags): shallow clones cannot resolve them.
*   The list is edited by hand: the policy is whatever is listed (one entry or many).
    Automation (e.g. deriving the list from release tags) can come later if the list becomes tedious to maintain.
*   The key is `baseline_refs` in `[tool.local_contract_test]` (decided).
    The reader can use `tomli` (already used by `local_test`).
*   See U2: the first baseline cannot be a release tag until a release contains `test_contract`.

### Reuse of integration tests (decided)

Many existing integration tests (`test_slow_integrated/`) use only public interfaces,
so they overlap with "old tests against new code".
They must still work as "new tests against new code".

*   The tests stay in the `protoprimer` package: `src/protoprimer/test/test_protoprimer/test_slow_integrated/test_contract/`.
    A **directory** (not a `pytest` marker) tells which tests are public-interface-only.
*   `local_contract_test` holds the machinery (runner, `venv` per ref, checks), not the tests.
*   The runner executes `pytest <that dir>` from the worktree of the old ref.
*   An old ref which does not have that dir **fails** (the baseline is not established, see U2).

### Methods of testing (decided)

*   **Old tests on new code** (`old_on_new`): old tests from a baseline ref run against the current code (see "Modes of running").
*   **Old artifact vs new venv** (`old_proto_on_new_venv`): old `proto_kernel.py` or old entry script run against the current `protoprimer`.
*   **New tests on new code** (`new_on_new`): the same tests in the current tree.
*   **Spec-based checks** (`cliff` for CLI, `griffe` for API, `pydantic` for config schema, the set of env var names)
    are ordinary tests in `test_contract`: they are part of the contract of a ref,
    so `old_on_new` runs the **old frozen** specs against the new code (see U4 for the remaining details).

Mapping of the parts of the interface to the methods:

| Part of the interface   | `old_on_new` (tests and frozen specs)   | `old_proto_on_new_venv` |
|-------------------------|-----------------------------------------|----------------|
| CLI                     | tests + `cliff` spec                    | yes            |
| Entry script and `wrap` | tests                                   | yes            |
| Config schema           | tests + `pydantic` schema               | no             |
| Env vars                | tests + names test                      | yes            |
| Bootstrap handoff       | no                                      | yes            |
| Python API              | `griffe` (U4, U7)                       | no             |

### Findings which affect how the tests can be reused

*   Fixtures always pair the same versions.
    `create_plain_proto_kernel` (`src/local_test/main/local_test/integrated_helper.py`)
    copies `proto_kernel.py` from the imported `protoprimer.primer_kernel.__file__`,
    and `create_test_pyproject_toml` installs `protoprimer @ file://<dir of the imported protoprimer>` into the `venv`.
    "Old proto vs new venv" needs a parameter for the source of `proto_kernel.py` (an old ref).

*   Old tests need their own old helpers.
    The tests depend on `local_test` helpers (`integrated_helper`, `fat_mocked_helper`, `name_assertion`, ...)
    which change over time: the old ref must provide its own `local_test`, while `protoprimer` must be the new one.
    Both are normally installed editable from the same tree, so the runner needs isolation (decided: a `venv` per ref, see the design).

*   Tests are not black-box.
    Most `slow` tests import internal-looking constants from `protoprimer.primer_kernel`
    (`ConfConstClient`, `ConfConstInput`, `ConfConstPrimer`, `ConfDst`, `TopDir`, `PathName`, `generate_entry_script_content`, ...)
    and build fixtures with them.
    Renaming such a constant breaks the old test even if the user-visible contract is unchanged (false positive).
    Decided: this is accepted and shrinking the public surface is a separate ongoing effort (see the decisions below).

*   `wrapped` only re-runs `slow` tests under `pyfakefs` (`fat_mock_wrapper`):
    e.g. `wrapped/test_op_boot.py` calls `slow/test_op_boot.py::test_op_boot`.
    It is the same contract test in a mocked perimeter - it is not a separate kind of test.
    A contract dir inside `slow` would be reused by `wrapped` automatically via import.

*   `slow` tests are skipped unless `CI` is set (`skip_test_slow_integrated`),
    and some need `requires_max_python`.

*   Some tests assert on the exact text of internal messages (e.g. `"cannot be from site packages"`, `"command failed with \`exit_code\`"`):
    only the exit code/the existence of a message is contract, not the text.

*   `test_relationship` and `assert_test_func_name_embeds_str` tie test names to enum values
    (e.g. `ExecOperation.op_boot.value`): a rename of the value is, in fact, a contract break, so these are fine.

### Decisions on the findings

*   Public surface of constants (`ConfConst*`, `TopDir`, `ConfDst`, ...):
    reducing it (making names private) is an ongoing effort and is not a concern of this plan.
    The compatibility testing only needs to **detect** a break;
    how it is fixed (e.g. making the name private and updating the tests) is up to the author of the change.
    Until the first stable version (`0.Y.Z`), such breaks are acceptable.

*   Message text vs exit codes: only the exit code and the presence of a message are contract.
    Defining exit codes in an enum is a separate related scope (see below, U8).

*   Config schema: a separate `local_config_schema` package (with its own `pyproject.toml`)
    defines the config schema (e.g. with `pydantic`) used only for testing.

*   API spec: `griffe` compares two importable public references
    (the baseline ref and the current code) to detect removed or changed public names.

*   Gaps to fill with new tests:
    old `proto_kernel.py` vs new `primer_kernel` in `venv`, full set of `EnvVar` names, schema spec, API spec.

*   In-process tests (`test_parse_args.py`, `pure/test_func_simple/`) are omitted for now:
    start with `test_slow_integrated/test_contract` only.

*   CLI: `cliff` tests are supposed to guard the CLI, but they have gaps
    (only `boot`/`reset`/`eval`, only `dest` compared, private parser factories used, no behavioral rules).
    Extend them instead of keeping `test_parse_args.py` as a contract test:
    see [TODO_01_84_56_96.cover_CLI_compatibility.md][TODO_01_84_56_96.cover_CLI_compatibility.md].

*   Entry script text: the exact generated content is **not** a public interface.
    Tests pinning it (`pure/test_func_simple/test_generate_entry_script_content.py`, `test_merge_entry_script_content.py`)
    stay as ordinary unit tests outside the contract set.
    The contract is the behavior of the entry script when it is run.
    `slow/test_op_wrap.py` compares the file against the output of `generate_entry_script_content` (circular):
    its contract version should assert that the file is executable and runs correctly.

*   Third handoff pairing: an **old entry script** (generated by a baseline ref and committed in a client repo)
    vs the new `proto_kernel.py` and `primer_kernel`.
    It uses the same baseline mechanism as the other two handoff categories.

## Design (draft)

Nothing here is implemented yet.
Statements about external tools (`griffe`, `git worktree`) are to be verified by a spike before relying on them.

### Packages

Like `local_test` and `local_repo`, the new packages are not publishable
(`Private :: Do Not Upload`, version `0.0.0`) and have their own `pyproject.toml` with `main/` (and `test/`):

```
src/local_contract_test/
    pyproject.toml
    main/local_contract_test/     # the runner: baseline refs, worktrees, spawning pytest, griffe check
    test/                    # tests of the runner itself (not the contract tests)

src/local_config_schema/
    pyproject.toml           # depends on `pydantic`
    main/local_config_schema/   # config schema models (testing only)
```

*   Both are registered like `local_test` is: `gconf/proto_kernel.json` (`build_root_dir_rel_path`) and the `dst/*_env` configs.
*   The contract tests themselves stay next to the code they test (decided):
    `src/protoprimer/test/test_protoprimer/test_slow_integrated/test_contract/`
    (later, for `metaprimer`: its own `test_contract` dir).
    `local_contract_test` holds the machinery, not the tests.
*   Baseline refs: `[tool.local_contract_test] baseline_refs` in `src/<project>/pyproject.toml` (see above).

### Modes of running

The three kinds of tests need different mechanisms, so there are three modes:

1.  **new tests on new code** (`new_on_new`): plain `pytest` on `test_contract` in the current tree.
    No `local_contract_test` machinery needed. This is the normal CI run.

2.  **old tests on new code** (`old_on_new`): checks that the contract did not change since the baseline.
    The contract of a ref is everything in its `test_contract` dir: behavior tests **and spec-based checks**
    (`cliff`, `griffe`, `pydantic`, env var names), so the old frozen specs run against the new code.

    *   For each `baseline_refs` item: `git worktree add --detach <tmp_dir>/<n> <ref>`
        (the current tree stays untouched; the worktree is removed afterwards).
        If the ref has no `test_contract` dir, the run **fails**: the baseline is not established.
        **UNCLEAR (U2):** whether this rule applies per mode and how the first baseline is established.
    *   A dedicated `venv` per ref (decided: no `PYTHONPATH` tricks - isolation must not be a gamble) with:
        *   the **old** `local_*` packages installed from the worktree (`local_test`, `local_repo`, `local_doc`):
            the old tests use their **own old helpers**;
        *   the **current** `protoprimer` (installed editable from the current tree).
    *   The `venv` is cached by the resolved commit id of the ref (the same ref is not rebuilt on every run).
    *   **UNDECIDED (U5):** `python` version, dependency pins, `CI=true`, cross-imports between test modules.
    *   Run `pytest` of that `venv` on `<worktree>/src/<project>/test/.../test_contract`.
    *   Result: old tests, old helpers, but `create_plain_proto_kernel` copies the **new** `primer_kernel.py` and
        `create_test_pyproject_toml` installs the **new** `protoprimer`.
        So it covers the "synced" case: new `proto_kernel.py` + new `venv` against an old contract.

3.  **old artifact vs new venv** (`old_proto_on_new_venv`): the handoff categories where the versions are intentionally different
    (old `proto_kernel.py`, or old entry script, vs new `protoprimer` in `venv`).

    *   Old tests cannot do this: their helpers always pair the same versions (see findings above).
        So these are **new** tests in `test_contract` which take the artifact from the baseline ref:
        `git show <ref>:src/protoprimer/main/protoprimer/primer_kernel.py`
        and run it standalone: `proto_kernel.py` is stand-alone and supports `wrap`,
        so the old entry script is generated by `python <old primer_kernel.py> wrap ...` (no import of the old `protoprimer` is needed).
    *   The helpers get explicit parameters instead of deriving everything from the imported `protoprimer`:
        the source of `proto_kernel.py` (default: current `primer_kernel.py`) and
        the dir of `protoprimer` installed into `venv` (default: current).
    *   The tests are parametrized by `baseline_refs`, so they run via `pytest` with a CLI option or env var holding the refs
        (no worktree is needed for the artifact itself).
    *   **UNDECIDED (U3):** where these tests live (not in `test_contract`, otherwise `old_on_new` re-runs them from old worktrees).

Spec-based checks are ordinary tests in `test_contract` (so they are part of `new_on_new` and `old_on_new`, not a separate run):

*   **API** (`griffe`): a test loads the public API from its own tree (for `old_on_new`: the old worktree,
    found via the test's `__file__`) and from the installed current `protoprimer`, and asserts there are no breaking changes
    (`griffe` reads source statically; the public/private line is `griffe`'s: names with a leading underscore are private).
    **UNDECIDED (U4):** loading two trees with the same package name is to be verified by a spike
    (fallback: a runner-driven `griffe check -a <ref>`, which also works for refs which predate the test).
    **UNDECIDED (U7):** how intended breaks are treated.
*   **CLI** (`cliff`): the spec is frozen in the ref, the new parser is compared against it.
    See [TODO_01_84_56_96.cover_CLI_compatibility.md][TODO_01_84_56_96.cover_CLI_compatibility.md].
*   **Config schema** (`pydantic`, `local_config_schema`): the old schema (installed from the ref into the runner `venv`)
    validates the configs produced by the new code.
    **UNDECIDED (U4):** which configs are checked.
*   **Env vars**: the old test pins the set of `EnvVar` names/values, the new code must still have all of them.

### Entry point

A command in `local_repo` style (`cmd_*.py` + `cmd/<name>` script), for example `cmd/contract_test` (**UNDECIDED (U6):** the name):

```shell
./cmd/contract_test --project protoprimer                # all modes, refs from `pyproject.toml`
./cmd/contract_test --project protoprimer --ref v0.0.2.final --mode old_on_new
```

*   `--ref` overrides the configured `baseline_refs` (any commit-ish).
*   The exit code is non-zero if anything is incompatible: **which means a `major` bump is needed** (or the change must be adjusted).
    **UNCLEAR (U1):** under `0.Y.Z` the suggestion should probably be `minor`.
*   The message printed on failure says this explicitly and shows which category failed.

### CI

*   Needs a full clone with tags (`fetch-depth: 0`), otherwise the refs cannot be resolved.
*   A separate job/workflow (not mixed with the `test_py_*` matrix): the `old_on_new` mode builds `venv`-s per ref and is slow.
*   Python version: start with `max` only; old tests may not run under `min`.

### Implementation steps (each is committed separately)

Blocked or affected by undecided points: step 2 (U2, U3), step 3 (U5), step 5 (U4, U7), step 7 (U4), step 8 (U1, U6).

1.  Package skeletons `local_contract_test` and `local_config_schema` registered in `gconf` / `dst`.
2.  Create `test_slow_integrated/test_contract/` and `git mv` the first public-interface-only tests
    (candidates are in the lists above). `wrapped/` imports these by module path - update the imports.
3.  Config reading (`baseline_refs`) + worktree helper + `venv`-per-ref + `old_on_new` runner.
4.  Parametrize the helpers (source of `proto_kernel.py`, dir of `protoprimer` to install) + the first `old_proto_on_new_venv` test.
5.  `griffe` API check (as a test in `test_contract`, after the spike); env var names test.
6.  Move the `cliff` test into `test_contract` and extend the CLI spec ([TODO_01_84_56_96.cover_CLI_compatibility.md][TODO_01_84_56_96.cover_CLI_compatibility.md]).
7.  `local_config_schema` + schema tests.
8.  `cmd/contract_test` and CI.
9.  Same for `metaprimer` (its baseline refs and tests).

### Decisions on design questions

*   A baseline ref without a `test_contract` dir: **fail** (the baseline is not established).
*   Scope: `protoprimer` only for now.
    The design stays flexible to test `metaprimer` later (it is publishable too):
    the project name is a parameter everywhere (`baseline_refs` per `pyproject.toml`, `--project`, the `test_contract` dir per project).
    Whether `metaprimer` runs against the current or the baseline `protoprimer` is to be decided then (separately, see U9).
*   Isolation of the old `local_test`: a `venv` per ref (see `old_on_new`).
*   Spec-based checks (`cliff`, `griffe`, `pydantic` schema, env var names) are tests in `test_contract` and run as part of `old_on_new`
    (the old frozen specs against the new code); there is no separate runner for them.
    Editing a spec in the new tree cannot hide a break from the baseline.
*   Exit codes enum: to be designed and implemented later together with the tests for it (**U8:** no TODO file yet).

## Undecided and unclear points

Status of this plan: the background, the scan and the design are written, **nothing is implemented**.
The points below are **not decided or not clear yet**.
Each is also marked in place with its ID (`U1`, `U2`, ...).
Remove an item from here (and its in-place marks) only when it is decided and recorded as a decision.

*   **U1. What the tool suggests under `0.Y.Z`.**
    The goal says "a major version increment is required".
    But the current version is `0.14.0.dev1`: in `semver`, anything may change in `0.Y.Z` and the usual bump is `minor` (`Y`).
    The message should probably say "bump `minor`" until `1.0.0`.
    Also `.dev1` is PEP 440, not `semver`: the mapping of the suggestion to the package version format is not defined.

*   **U2. How the first baseline is established.**
    No release contains `test_contract` yet, so a release tag cannot be a baseline until a release after implementation step 2 exists.
    Until then, a commit-ish (branch or commit id) has to be used.
    Related: "a baseline ref without a `test_contract` dir fails" is decided,
    but `old_proto_on_new_venv` mode needs only `primer_kernel.py` from the ref, not `test_contract`:
    it is not defined whether the "fail" rule applies per mode or to the whole run.

*   **U3. Where the `old_proto_on_new_venv` tests live.**
    If they are in `test_contract`, the `old_on_new` mode re-runs them from old worktrees,
    where there is no baseline config (it is read from the current tree).
    They probably need a separate directory (the directory is the marker), but its name and location are not decided.

*   **U4. Remaining details of the spec-based checks (the main decision is made, see "Decisions on design questions").**
    *   `griffe`: loading two trees with the same package name (old worktree vs installed current) in one test is **not verified**:
        needs a spike (fallback: a runner-driven `griffe check -a <ref>`).
    *   `local_config_schema`: its content is not defined.
        Config **acceptance** is already covered by old tests (old helpers write old-format configs and the new code must accept them),
        so the schema adds: the new code's generated configs/defaults still validate against the **old frozen** schema.
        Which configs are checked is not defined.
    *   The `cliff` test (today in `local_test`) has to move to `test_contract`;
        what to do with the `check` command in the spec is open in
        [TODO_01_84_56_96.cover_CLI_compatibility.md][TODO_01_84_56_96.cover_CLI_compatibility.md].

*   **U5. Details of the per-ref runner `venv` (`old_on_new`).**
    *   Which `python` is used and which dependency pins (e.g. the old ref's `version_constraints.txt` or the current ones).
    *   The runner must set `CI=true` (otherwise `test_slow_integrated` tests are skipped) and satisfy `requires_max_python`.
    *   Some `slow` tests import other test modules (e.g. `KeyWord` from `test_primer_kernel_metadata`):
        is a cross-import from a contract test to a non-contract test acceptable?

*   **U6. Names.**
    `local_contract_test` is the package name (decided).
    Not decided: whether the `test_contract` directory and the `cmd/contract_test` command should be renamed to match.

*   **U7. The initial flood of `griffe` findings.**
    `primer_kernel.py` has no `__all__`, so every name without a leading underscore is public.
    Shrinking this surface is an ongoing effort (decided), but it is not defined how the check treats breaks
    which are intended (e.g. making a name private): fail until the baseline moves, or a list of accepted breaks.

*   **U8. Exit codes enum has no TODO file yet.**
    It is only an item in "Related scopes (outside this plan)".

*   **U9. `metaprimer` (deferred by decision).**
    Whether `metaprimer` is tested against the current or the baseline `protoprimer` will be decided when `metaprimer` is added.
