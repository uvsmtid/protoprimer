## Background

### Goal

Automatically detect backward-incompatible changes, so that a failing compatibility test means:
"the changes break backward compatibility tests in the baseline".
Possible actions:

*   [A] fix the changes to comply;
*   [B] update the baseline.

### What is special about `protoprimer`

`protoprimer` is not a plain library: it bootstraps an environment through a hosted script.

*   [proto_kernel.py][FT_87_17_49_36.proto_kernel.md] is a copy of `protoprimer.primer_kernel`
    committed into the client repo (see [runtime][runtime.md]).
    It is pinned to whatever version was copied, and it is **not** updated with the `protoprimer` package.

*   `proto_kernel.py` starts working **before** `venv` exists.
    Once `venv` is created and `protoprimer` is installed there,
    `protoprimer.primer_kernel` from `venv` takes over
    (see [primer_runtime][FT_14_52_73_23.primer_runtime.md]).

*   Therefore, at any moment, two *different versions* of the same code base may cooperate within one bootstrap sequence:
    an old `proto_kernel.py` and a new (or old) `protoprimer.primer_kernel`.

Consequence: compatibility must be verified in two independent dimensions
(the second one is specific to `protoprimer`):
*   public interface compatibility,
*   bootstrap handoff compatibility.

### Kinds of compatibility

1.  **Public interface** compatibility (the classical `semver` case, see [backward_compatibility][FT_78_72_23_04.backward_compatibility.md]).
    Parts of the interface under test:

    *   API: public entries in `protoprimer.primer_kernel`
    *   CLI: args handled by `parse_args` (see `EnvState.state_args_parsed`, [CLI_compatibility][FT_62_88_55_10.CLI_compatibility.md])
    *   config schema: config files (e.g. `lconf`, `gconf`)
    *   env vars: `EnvVar` (see [env_var][FT_08_92_69_92.env_var.md]) - used by users **and** to propagate info across processes during bootstrap

2.  **Bootstrap handoff** compatibility:
    existing `proto_kernel.py` (old copy) vs `protoprimer.primer_kernel` from `venv` (new code).
    Parts of the interface under test:

    *   the data exchanged during the bootstrap sequence: CLI args, env vars, files/dirs (e.g. `venv`, `cache`, config), exit codes
    *   the `switch`/re-exec sequence from `proto_kernel.py` into `venv` (see [boot_vs_start][FT_58_74_37_70.boot_vs_start.md], [entry_script][FT_75_87_82_46.entry_script.md])

    `venv` is **not** a prerequisite of this testing: `proto_kernel.py` works before `venv` exists,
    so the old script can be tested against new code both with and without a pre-created `venv`.

    The same applies to an **old entry script** (generated by a baseline commit name and committed in a client repo):
    it calls `proto_kernel.py` and must keep working with the new code (see `old_entry_on_new_proto` in "Modes (ids)").

### Modes (ids)

Every way of running compatibility checks has an id.
The id is used everywhere in this plan (and is planned as the `--mode` value of the runner CLI).
A mode is defined by **where each part comes from**: the tests/specs, `proto_kernel.py` (with the entry script), and `protoprimer` installed in `venv`.

| Mode id                  | Tests and specs come from                    | `proto_kernel.py` comes from | Entry script comes from      | `protoprimer` in `venv` comes from |
|--------------------------|----------------------------------------------|------------------------------|------------------------------|------------------------------------|
| `new_tests_on_new_changes`             | current tree                                 | current tree                 | current tree (generated)     | current tree                       |
| `old_tests_on_new_changes`             | baseline commit name (its `test_contract_compatibility` dir)       | current tree                 | current tree (generated)     | current tree                       |
| `old_proto_on_new_venv`  | current tree (new tests, per baseline commit name)   | baseline commit name                 | baseline commit name (via old `wrap`) | current tree                      |
| `old_entry_on_new_proto` | current tree (new tests, per baseline commit name)   | current tree                 | baseline commit name                 | current tree                       |

*   `new_tests_on_new_changes`: **new tests on new changes**.
    The normal run of `test_contract_compatibility` in the current tree (tests and spec-based checks).
    The versions are synced: new `proto_kernel.py` (outside `venv`) and new `protoprimer.primer_kernel` in `venv`.

*   `old_tests_on_new_changes`: **old tests (and frozen specs) on new changes**.
    Everything a baseline commit name defines as its contract (behavior tests **and** spec-based checks) runs against the current code.
    This answers: "did the public interface (API, CLI, config schema, env vars, behavior) change since the baseline?"
    The versions are synced (both are new), but the expectations are old.

*   `old_proto_on_new_venv`: **old `proto_kernel.py` on new `venv`**.
    Can an old `proto_kernel.py` (e.g. kept in a client repo) bootstrap into the new `protoprimer`
    (with its new `protoprimer.primer_kernel`)?
    `proto_kernel.py` and `protoprimer.primer_kernel` are copies only when synced;
    while they are not synced yet (or a client repo keeps an old copy), they must remain interoperable.

*   `old_entry_on_new_proto`: **old entry script on new `proto_kernel.py` and new `venv`**.
    An entry script generated by a baseline commit name (and committed in a client repo) keeps working with the new code.
    (The exact text of the entry script is not public interface, its behavior when run is.)

Both `old_proto_on_new_venv` and `old_entry_on_new_proto` need an old artifact which old tests cannot provide
(their helpers always pair the same versions): they are new tests, see the design.

### Baseline commit names configuration (decided)

The baseline is any commit-ish string (branch name, tag name, commit id, etc.).
It is configured in the `pyproject.toml` of each releasable project under test
(`src/protoprimer/pyproject.toml` and `src/metaprimer/pyproject.toml`)
in a tool-specific table (PEP 518 reserves `[tool.*]` for this), for example:

```toml
[tool.local_contract_compatibility]
baseline_commit_names = [
    "HEAD",
]
```

*   Each project has its own list: they are released separately and their tags have different prefixes.
*   The config is read from the current tree (new code), not from the baseline commit name.
*   CI must fetch the commit names (full clone with tags): shallow clones cannot resolve them.
*   It is a list so that more entries can be added without changing the format
    (old copies of `proto_kernel.py` in client repos, compatibility is not transitive between releases),
    but it starts with **one** entry (every extra entry adds ~9 minutes of `old_tests_on_new_changes` per commit name).
*   The list is edited by hand: the policy is whatever is listed (one entry or many).
    Automation (e.g. deriving the list from release tags) can come later if the list becomes tedious to maintain.
*   The key is `baseline_commit_names` in `[tool.local_contract_compatibility]` (decided).
    The reader can use `tomli` (already used by `local_test`).
*   The initial entry is `HEAD` (whatever is current):
    `old_tests_on_new_changes` then effectively runs the same tests as `new_tests_on_new_changes`
    (the committed state; uncommitted changes in the working tree are not in the worktree of `HEAD`),
    so it exercises the machinery but cannot detect a break.
    It is replaced by a real older commit name (e.g. a release tag) once a release contains `test_contract_compatibility`.

### Reuse of integration tests (decided)

Many existing integration tests (`test_slow_integrated/`) use only public interfaces,
so they overlap with `old_tests_on_new_changes`.
They must still work as `new_tests_on_new_changes`.

*   The tests stay in the `protoprimer` package: `src/protoprimer/test/test_protoprimer/test_slow_integrated/test_contract_compatibility/`.
    A **directory** (not a `pytest` marker) tells which tests are public-interface-only.
*   `local_contract_compatibility` holds the machinery (runner, `venv` per commit name, checks), not the tests.
*   The runner executes `pytest <that dir>` from the worktree of the old commit name.
*   An old commit name which does not have that dir **fails** (the baseline is not established).

See [test_perimeter][FT_83_60_72_19.test_perimeter.md] for the existing test dir layout
(`test_slow_integrated`, `test_fast_fat_min_mocked`, ...) which the new directory fits into.

### Methods of testing (decided)

Modes are defined in "Modes (ids)" above; the mechanisms are in "Modes of running" in the design.

*   `new_tests_on_new_changes`, `old_tests_on_new_changes`: tests in `test_contract_compatibility`, run from the current tree or from a baseline commit name.
*   `old_proto_on_new_venv`, `old_entry_on_new_proto`: new tests which take an old `proto_kernel.py`/entry script from a baseline commit name.
*   **Spec-based checks** (`cliff` for CLI, `griffe` for API, `pydantic` for config schema, the set of env var names)
    are ordinary tests in `test_contract_compatibility`: they are part of the contract of a commit name,
    so `old_tests_on_new_changes` runs the **old frozen** specs against the new code (see U4 for the remaining details).

Mapping of the parts of the interface to the methods:

| Part of the interface   | `old_tests_on_new_changes` (tests and frozen specs) | `old_proto_on_new_venv` | `old_entry_on_new_proto` |
|-------------------------|---------------------------------------|-------------------------|--------------------------|
| CLI                     | tests + `cliff` spec                  | yes                     | no                       |
| Entry script and `wrap` | tests                                 | yes                     | yes                      |
| Config schema           | tests + `pydantic` schema             | no                      | no                       |
| Env vars                | tests + names test                    | yes                     | no                       |
| Bootstrap handoff       | no                                    | yes                     | yes                      |
| Python API              | `griffe` (U4, U7)                     | no                      | no                       |

### Findings which affect how the tests can be reused

*   Fixtures always pair the same versions.
    `create_plain_proto_kernel` (`src/local_test/main/local_test/integrated_helper.py`)
    copies `proto_kernel.py` from the imported `protoprimer.primer_kernel.__file__`,
    and `create_test_pyproject_toml` installs `protoprimer @ file://<dir of the imported protoprimer>` into the `venv`.
    `old_proto_on_new_venv` needs a parameter for the source of `proto_kernel.py` (an old commit name).

*   Tests in `old_tests_on_new_changes` need their own old helpers.
    The tests depend on `local_test` helpers (`integrated_helper`, `fat_mocked_helper`, `name_assertion`, ...)
    which change over time: the old commit name must provide its own `local_test`, while `protoprimer` must be the new one.
    Both are normally installed editable from the same tree, so the runner needs isolation (decided: a `venv` per commit name, see the design).

*   Tests are not black-box.
    Most `slow` tests import internal-looking constants from `protoprimer.primer_kernel`
    (`ConfConstClient`, `ConfConstInput`, `ConfConstPrimer`, `ConfDst`, `TopDir`, `PathName`, `generate_entry_script_content`, ...)
    and build fixtures with them.
    Renaming such a constant breaks the old test even if the user-visible contract is unchanged (false positive).
    Decided: this is accepted and shrinking the public surface is a separate ongoing effort (see the decisions below).

*   `wrapped` only re-runs `slow` tests under `pyfakefs` (`fat_mock_wrapper`):
    e.g. `wrapped/test_op_boot.py` calls `slow/test_contract_compatibility/test_op_boot.py::test_op_boot`.
    It is the same contract test in a mocked perimeter - it is not a separate kind of test.
    A contract dir inside `slow` would be reused by `wrapped` automatically via import.

*   `slow` tests are skipped unless `CI` is set (`skip_test_slow_integrated`),
    and some need `requires_max_python`.

*   Some tests assert on the exact text of internal messages (e.g. `"cannot be from site packages"`, `"command failed with \`exit_code\`"`):
    only the exit code/the existence of a message is contract, not the text.

*   `test_relationship` and `assert_test_func_name_embeds_str` tie test names to enum values
    (e.g. `ExecOperation.op_boot.value`): a rename of the value is, in fact, a contract break, so these are fine.

### Decisions on the findings

*   Public surface of constants (`ConfConst*`, `TopDir`, `ConfDst`, ...):
    reducing it (making names private) is an ongoing effort and is not a concern of this plan.
    The compatibility testing only needs to **detect** a break;
    how it is fixed (e.g. making the name private and updating the tests) is up to the author of the change.
    Until the first stable version (`0.Y.Z`), such breaks are acceptable.

*   Message text vs exit codes: only the exit code and the presence of a message are contract.
    Defining exit codes in an enum is a separate related scope (see below, U8).

*   Config schema: a separate `local_config_schema` package (with its own `pyproject.toml`)
    defines the config schema (e.g. with `pydantic`) used only for testing.

*   API spec: `griffe` compares two importable public references
    (the baseline commit name and the current code) to detect removed or changed public names.

*   Gaps to fill with new tests:
    `old_proto_on_new_venv`, `old_entry_on_new_proto`, full set of `EnvVar` names, schema spec, API spec.

*   In-process tests (`test_parse_args.py`, `pure/test_func_simple/`) are omitted for now:
    start with `test_slow_integrated/test_contract_compatibility` only.

*   CLI: `cliff` tests are supposed to guard the CLI, but they have gaps
    (only `boot`/`reset`/`eval`, only `dest` compared, private parser factories used, no behavioral rules).
    Extend them instead of keeping `test_parse_args.py` as a contract test:
    see [TODO_01_84_56_96.cover_CLI_compatibility.md][TODO_01_84_56_96.cover_CLI_compatibility.md].

*   Entry script text: the exact generated content is **not** a public interface.
    Tests pinning it (`pure/test_func_simple/test_generate_entry_script_content.py`, `test_merge_entry_script_content.py`)
    stay as ordinary unit tests outside the contract set.
    The contract is the behavior of the entry script when it is run.
    `slow/test_not_contract_compatibility/test_op_wrap.py` compares the file against the output of `generate_entry_script_content` (circular):
    its contract version should assert that the file is executable and runs correctly.

*   The old entry script is a separate mode, `old_entry_on_new_proto`
    (an entry script generated by a baseline commit name and committed in a client repo vs the new `proto_kernel.py` and `primer_kernel`).
    It uses the same baseline mechanism as the other modes.

    `test_plain_proto_kernel_help`, `test_invalid_args_primer_kernel`, `test_trace_mode`, `test_context_isolation`.
*   `slim/test_argparse/test_parse_args.py` and `pure/test_func_simple/` are in-process API/CLI tests:
    they would need the old test file run against the new module, without any subprocess or `venv`.
    They would need their own sub-dir in `slim` and `pure` if the directory is the marker.
*   `wrapped` needs no marker of its own (it imports from `slow`).

## Design (draft)

Nothing here is implemented yet.
The main assumptions about external tools (`griffe` on two trees, `git worktree` + `venv` per commit name) were verified by two spikes (see "Spike results").

### Packages

Like `local_test` and `local_repo`, the new packages are not publishable
(`Private :: Do Not Upload`, version `0.0.0`) and have their own `pyproject.toml` with `main/` (and `test/`):

```
src/local_contract_compatibility/
    pyproject.toml
    main/local_contract_compatibility/     # the runner: baseline commit names, worktrees, spawning pytest, griffe check
    test/                    # tests of the runner itself (not the contract tests)

src/local_config_schema/
    pyproject.toml           # depends on `pydantic`
    main/local_config_schema/   # config schema models (testing only)
```

*   Both are registered like `local_test` is: `gconf/proto_kernel.json` (`build_root_dir_rel_path`) and the `dst/*_env` configs.
*   The contract tests themselves stay next to the code they test (decided):
    `src/protoprimer/test/test_protoprimer/test_slow_integrated/test_contract_compatibility/`
    (later, for `metaprimer`: its own `test_contract_compatibility` dir).
    `local_contract_compatibility` holds the machinery, not the tests.
*   Baseline commit names: `[tool.local_contract_compatibility] baseline_commit_names` in `src/<project>/pyproject.toml` (see above).

### Modes of running (mechanisms)

The modes are defined in "Modes (ids)". Their mechanisms differ, so each is described here.

1.  `new_tests_on_new_changes`: plain `pytest` on `test_contract_compatibility` in the current tree.
    No `local_contract_compatibility` machinery needed. This is the normal CI run.

2.  `old_tests_on_new_changes`: checks that the contract did not change since the baseline.
    The contract of a commit name is everything in its `test_contract_compatibility` dir: behavior tests **and spec-based checks**
    (`cliff`, `griffe`, `pydantic`, env var names), so the old frozen specs run against the new code.

    *   For each `baseline_commit_names` item: `git worktree add --detach <tmp_dir>/<n> <commit_name>`
        (the current tree stays untouched; the worktree is removed afterwards).
        If the commit name has no `test_contract_compatibility` dir, the run **fails**: the baseline is not established.
        Each mode checks its own inputs (`old_proto_on_new_venv` and `old_entry_on_new_proto` need only `primer_kernel.py`),
        a missing input fails that mode only, the other modes still run, and the final report shows each mode separately;
        the run exits non-zero if any mode failed.
    *   A dedicated `venv` per commit name (decided: no `PYTHONPATH` tricks - isolation must not be a gamble) with:
        *   the **old** `local_*` packages installed from the worktree (`local_test`, `local_repo`, `local_doc`):
            the old tests use their **own old helpers**;
        *   the **current** `protoprimer` (installed editable from the current tree).
    *   The `venv` is cached by the resolved commit id of the commit name (the same commit name is not rebuilt on every run).
    *   **UNDECIDED (U5):** `python` version, dependency pins, `CI=true`, cross-imports between test modules.
    *   Run `pytest` of that `venv` on `<worktree>/src/<project>/test/.../test_contract_compatibility`.
    *   Result: old tests, old helpers, but `create_plain_proto_kernel` copies the **new** `primer_kernel.py` and
        `create_test_pyproject_toml` installs the **new** `protoprimer`.

3.  `old_proto_on_new_venv` and 4. `old_entry_on_new_proto`: the versions are intentionally different.

    *   Old tests cannot do this: their helpers always pair the same versions (see findings above).
        So these are **new** tests in `test_contract_compatibility` which take the old `proto_kernel.py` (or entry script) from the baseline commit name:
        `git show <commit_name>:src/protoprimer/main/protoprimer/primer_kernel.py`
        and run it standalone: `proto_kernel.py` is stand-alone and supports `wrap`,
        so the old entry script is generated by `python <old primer_kernel.py> wrap ...` (no import of the old `protoprimer` is needed).
    *   The helpers get explicit parameters instead of deriving everything from the imported `protoprimer`:
        the source of `proto_kernel.py` (default: current `primer_kernel.py`) and
        the dir of `protoprimer` installed into `venv` (default: current).
    *   The tests are parametrized by `baseline_commit_names`, so they run via `pytest` with a CLI option or env var holding the commit names
        (no worktree is needed for the old `proto_kernel.py` itself).
    *   They live in separate directories, one per mode and named after the mode id
        (siblings of `test_contract_compatibility` in `test_slow_integrated`):
        `test_old_proto_on_new_venv/` and `test_old_entry_on_new_proto/`.
        `old_tests_on_new_changes` never runs them from old worktrees;
        they are parametrized by `baseline_commit_names` and are skipped in a normal `pytest` run;
        the `compat` CI job enables them (see "CI").

Spec-based checks are ordinary tests in `test_contract_compatibility` (so they are part of `new_tests_on_new_changes` and `old_tests_on_new_changes`, not a separate mode):

*   **API** (`griffe`): a test loads the public API from its own tree (for `old_tests_on_new_changes`: the old worktree,
    found via the test's `__file__`) and from the installed current `protoprimer`, and asserts there are no breaking changes
    (`griffe` reads source statically; the public/private line is `griffe`'s: names with a leading underscore are private).
    Verified by the spike ex_1 (see "Spike results").
    A runner-driven `griffe check -a <commit_name>` also works and covers commit names which predate the test.
    **DEFERRED (U7):** no kind of finding is ignored for now: the check is adjusted once the tests are in place and their failures are addressed.
*   **CLI** (`cliff`): the spec is frozen in the commit name, the new parser is compared against it.
    See [TODO_01_84_56_96.cover_CLI_compatibility.md][TODO_01_84_56_96.cover_CLI_compatibility.md].
*   **Config schema** (`pydantic`, `local_config_schema`): the old schema (installed from the commit name into the runner `venv`)
    validates the configs produced by the new code.
    **UNDECIDED (U4):** which configs are checked.
*   **Env vars**: the old test pins the set of `EnvVar` names/values, the new code must still have all of them.

### Entry point

A command in `local_repo` style (`cmd_*.py` + `cmd/<name>` script), for example `cmd/test_contract_compatibility`:

```shell
./cmd/test_contract_compatibility --package_name protoprimer                # all modes, commit names from `pyproject.toml`
./cmd/test_contract_compatibility --package_name protoprimer --commit_name v0.0.2.final --mode old_tests_on_new_changes
```

*   `--mode` takes the mode ids from "Modes (ids)": `new_tests_on_new_changes`, `old_tests_on_new_changes`, `old_proto_on_new_venv`, `old_entry_on_new_proto`.
    The default is all of them.

*   `--commit_name` overrides the configured `baseline_commit_names` (any commit-ish).
*   The exit code is non-zero if anything is incompatible.
*   The message printed on failure says: "the changes break backward compatibility tests in the baseline -
    possible actions: [A] fix changes to comply [B] update the baseline",
    and shows which mode and category failed.
    It does not suggest which version to bump.

### CI

*   The compatibility modes which use `baseline_commit_names`
    (`old_tests_on_new_changes`, `old_proto_on_new_venv`, `old_entry_on_new_proto`)
    run in their own job with the label `compat`, under the `max` python version only.
    The workflow is `.github/workflows/test_contract_compatibility.yaml` (following the existing pattern, like `lint.yaml` and `doc.yaml`),
    and its badge in `readme.md` is placed between `py[max]` and `lint`.
    Done: the workflow runs `./cmd/test_contract_compatibility --package_name protoprimer` with `fetch-depth: 0`, and the badge exists.
*   They are **not** run in the `py[min]`, `py[med]`, `py[max]` jobs, which stay symmetric:
    those jobs run only the default mode `new_tests_on_new_changes` (all tests, without any compatibility testing against a baseline).
    The compatibility tests are not supposed to fail due to the `python` version
    if they already succeed in `new_tests_on_new_changes`, so running them in all three versions would be overkill.
*   Consequence: the `old_proto_on_new_venv` and `old_entry_on_new_proto` tests (parametrized by `baseline_commit_names`)
    must be skipped by default in a normal `pytest` run and enabled only by the `compat` job:
    the `py[*]` jobs do not have the full git history needed to resolve commit names.
*   The `compat` job needs a full clone with tags (`fetch-depth: 0`), otherwise the commit names cannot be resolved.
*   It is slow: `old_tests_on_new_changes` builds a `venv` per commit name
    (measured: ~9 minutes per commit name for the full `test_slow_integrated`, see U5).

### Spike results

Two throwaway spikes were done on separate branches (scripts and detailed results are in their `readme.md`):

*   Branch `semver_compatibility_testing.ex_1.griffe_tree`, `spike/ex_1/`: `griffe` on two trees with the same package name.
    *   Works in one process (~0.2s), the trees do not shadow each other, nothing is imported (static analysis),
        a tree compared with itself gives 0 findings.
    *   `protoprimer-v0.13.0.final` vs the current tree: 55 findings; the real renames (`proto_code` to `proto_kernel`) are caught.
        33 of 55 are `Attribute value was changed` noise (source text of enum values is compared): see U7.
    *   `griffe check -a <commit_name>` works as well (the fallback).

*   Branch `semver_compatibility_testing.ex_2.ref_venv`, `spike/ex_2/`: a `venv` per commit name runs old tests on new changes.
    *   Worktree of the baseline + a `venv` with the old `local_test`/`local_repo`/`local_doc` (installed from the worktree)
        and the current `protoprimer` (editable); no `PYTHONPATH` tricks needed; `CI=true` required.
    *   Baseline `main` (same `src` as the current branch): all 52 tests of `test_slow_integrated` passed (8m46s).
    *   Baseline `protoprimer-v0.13.0.final` (before the `proto_code` to `proto_kernel` concept fix): 18 tests (not the whole directory)
        passed against the current code, although `griffe` reports 20 removed names for the same pair:
        API surface changes and behavior changes are different questions, so both checks are needed.
    *   Not covered: `python` min/med, pinned dependencies, `metaprimer`, a baseline whose tests fail against the new code.

### Decisions on design questions

*   A baseline commit name without a `test_contract_compatibility` dir: **fail** (the baseline is not established).
*   Scope: `protoprimer` only for now.
    The design stays flexible to test `metaprimer` later (it is publishable too):
    the project name is a parameter everywhere (`baseline_commit_names` per `pyproject.toml`, `--package_name`, the `test_contract_compatibility` dir per project).
    Whether `metaprimer` runs against the current or the baseline `protoprimer` is to be decided then (separately, see U9).
*   The `old_proto_on_new_venv` and `old_entry_on_new_proto` tests live in separate directories named after the mode ids,
    siblings of `test_contract_compatibility` in `test_slow_integrated`: `test_old_proto_on_new_venv/`, `test_old_entry_on_new_proto/`.
    `old_tests_on_new_changes` does not run them from old worktrees.
    They are skipped in a normal `pytest` run and enabled by the `compat` CI job.
*   Isolation of the old `local_test`: a `venv` per commit name (see `old_tests_on_new_changes`).
*   Spec-based checks (`cliff`, `griffe`, `pydantic` schema, env var names) are tests in `test_contract_compatibility` and run as part of `old_tests_on_new_changes`
    (the old frozen specs against the new code); there is no separate runner for them.
    Editing a spec in the new tree cannot hide a break from the baseline.
*   CI: the modes which use `baseline_commit_names` run in a separate `compat` job (under `max` python only),
    not in `py[min]`/`py[med]`/`py[max]`, which stay symmetric and run only `new_tests_on_new_changes` (see "CI").
*   One list for all modes: each mode checks its own inputs, fails separately, the other modes still run,
    the run is non-zero if any mode failed.
    The initial entry is `HEAD` (see "Baseline commit names configuration").
*   Failure message: the changes break backward compatibility tests in the baseline;
    possible actions: [A] fix changes to comply, [B] update the baseline. No version bump is suggested.
*   Exit codes enum: to be designed and implemented later together with the tests for it (**U8:** no TODO file yet).

## Undecided and unclear points

Status of this plan: the background, the scan and the design are written, **nothing is implemented**.
The points below are **not decided or not clear yet**.
Each is also marked in place with its ID (`U4`, `U5`, ...).
Remove an item from here (and its in-place marks) only when it is decided and recorded as a decision.

*   **U4. Remaining details of the spec-based checks (the main decision is made, see "Decisions on design questions").**
    *   `griffe`: loading two trees with the same package name in one test is **verified** (spike ex_1, see "Spike results"):
        no open question remains about loading.
    *   `local_config_schema`: its content is not defined.
        Config **acceptance** is already covered by old tests (old helpers write old-format configs and the new code must accept them),
        so the schema adds: the new code's generated configs/defaults still validate against the **old frozen** schema.
        Which configs are checked is not defined.
    *   The `cliff` test (today in `local_test`) has to move to `test_contract_compatibility`;
        what to do with the `check` command in the spec is open in
        [TODO_01_84_56_96.cover_CLI_compatibility.md][TODO_01_84_56_96.cover_CLI_compatibility.md].

*   **U5. Remaining details of the per-commit-name runner `venv` (`old_tests_on_new_changes`).**
    The mechanism is verified (spike ex_2, see "Spike results"). Open:
    *   Which `python` versions (only 3.14 was tried; `min`/`med` are not) and which dependency pins
        (the spike used unpinned dependencies from PyPI: the old commit name's `version_constraints.txt` or the current ones?).
    *   The runner must set `CI=true` (confirmed: otherwise `test_slow_integrated` tests are skipped) and satisfy `requires_max_python`.
    *   Time: the full `test_slow_integrated` takes ~9 minutes per commit name (plus ~25s to build the `venv`):
        run all of it per commit name or a subset? This matters for how many commit names can be in `baseline_commit_names`.
    *   Cross-imports between test modules worked in the spike (the whole old tree is in the worktree),
        but whether it is acceptable for the contract to depend on non-contract test modules is not decided.

*   **U7. The initial flood of `griffe` findings.**
    `primer_kernel.py` has no `__all__`, so every name without a leading underscore is public.
    Shrinking this surface is an ongoing effort (decided), but it is not defined how the check treats breaks
    which are intended (e.g. making a name private): fail until the baseline moves, or a list of accepted breaks.
    The spike showed the scale: 55 findings between `protoprimer-v0.13.0.final` and the current tree (20 removed names),
    and 33 of them are noise (`Attribute value was changed` compares the source text of enum values, not the values):
    that kind has to be filtered or ignored, or the enums made private (a private name is not compared by `griffe`).
    **Deferred by decision:** nothing is ignored yet; the check is adjusted once the tests are in place and their failures are addressed.
    Also, the removed names did not break any behavior test: `griffe` reports API surface changes, not behavior changes.

*   **U8. Exit codes enum has no TODO file yet.**
    It is only an item in "Related scopes (outside this plan)".

*   **U9. `metaprimer` (deferred by decision).**
    Whether `metaprimer` is tested against the current or the baseline `protoprimer` will be decided when `metaprimer` is added.
