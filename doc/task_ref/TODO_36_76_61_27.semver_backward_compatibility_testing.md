## Background

### Modes by inputs

A mode is defined by **where each part comes from**: the tests/specs, `proto_kernel.py` (with the entry script), and `protoprimer` installed in `venv`.

| Mode id                    | Tests and specs come from                                    | `proto_kernel.py` comes from | Entry script comes from               | `protoprimer` in `venv` comes from |
|----------------------------|--------------------------------------------------------------|------------------------------|---------------------------------------|------------------------------------|
| `new_tests_on_new_changes` | current tree                                                 | current tree                 | current tree (generated)              | current tree                       |
| `old_tests_on_new_changes` | baseline commit name (its `test_contract_compatibility` dirs) | current tree                 | current tree (generated)              | current tree                       |
| `old_proto_on_new_venv`    | current tree (reused, per baseline commit name)              | baseline commit name         | baseline commit name (via old `wrap`) | current tree                       |
| `old_entry_on_new_proto`   | current tree (reused, per baseline commit name)              | current tree                 | baseline commit name                  | current tree                       |

Old tests cannot provide an old artifact for `old_proto_on_new_venv` and `old_entry_on_new_proto`
(their helpers always pair the same versions), so these modes reuse the current tests with one input swapped.

### Mapping of the interface parts to the modes

| Part of the interface   | `old_tests_on_new_changes` (tests and frozen specs) | `old_proto_on_new_venv` | `old_entry_on_new_proto` |
|-------------------------|-----------------------------------------------------|-------------------------|--------------------------|
| CLI                     | tests + `cliff` spec                                | yes                     | no                       |
| Entry script and `wrap` | tests                                               | yes                     | yes                      |
| Config schema           | tests + `pydantic` schema                           | no                      | no                       |
| Env vars                | tests + names test                                  | yes                     | no                       |
| Bootstrap handoff       | no                                                  | yes                     | yes                      |
| Python API              | `griffe`                                            | no                      | no                       |

### Baseline: reasons

*   Each project has its own list: they are released separately and their tags have different prefixes.
*   It is a list because compatibility is not transitive between releases (old copies of `proto_kernel.py` stay in client repos).
    It starts with **one** entry: every extra entry adds ~9 minutes of `old_tests_on_new_changes` per commit name.
*   The list is edited by hand; automation (e.g. deriving it from release tags) can come later if it becomes tedious.
*   `HEAD` exercises the machinery but cannot detect a break.
    Replace it by a real older commit name (e.g. a release tag) once a release contains `test_contract_compatibility`.

## Decisions

*   Internal tests may use internals (they are not black-box): renaming a constant breaks an old test even if the user-visible contract is unchanged.
    This is accepted; shrinking the public surface is a separate effort
    ([TODO_72_65_47_51.reduce_public_interface_surface.md][TODO_72_65_47_51.reduce_public_interface_surface.md]).
    The compatibility testing only **detects** a break; how it is fixed is up to the author of the change.
    Until the first stable version (`0.Y.Z`), such breaks are acceptable.

*   Message text vs exit codes: only the exit code and the presence of a message are contract (the enum is U8).

*   Entry script text is not public interface, its behavior when run is.
    Tests pinning the generated text stay as ordinary unit tests outside the contract set.

*   In-process tests (`test_parse_args.py`, `test_func_simple/`) are not contract tests:
    the CLI is covered by the `cliff` spec ([TODO_01_84_56_96.cover_CLI_compatibility.md][TODO_01_84_56_96.cover_CLI_compatibility.md]).

*   `griffe` findings: no special mechanism (no accepted-breaks allowlist, no filter).
    An intentional break is handled like any other: [A] fix the change to comply, or [B] move the baseline past it.
    Making a name private (`TODO_72_65_47_51`) removes it from the comparison.

*   Config schema scope: `local_config_schema` validates `ConfLeap.leap_primer`, `leap_client` and `leap_env` -
    the only leaps with an actual config file today. `leap_input`/`leap_derived` are surrogates (no file to validate);
    `leap_global`/`leap_local` are being renamed/removed (`TODO_39_94_67_54`), so excluded for now.

*   A baseline which lacks a contract dir or an old `local_*` package **fails** ("the baseline is not established"); nothing is skipped silently.

*   Scope: `protoprimer` only for now. The project name is a parameter everywhere
    (`baseline_commit_names` per `pyproject.toml`, `--package_name`, the `test_contract_compatibility` dir per project),
    so `metaprimer` can be added later.
