TODO: TODO_25_82_21_54.rename_is_app_flag.md

Rename `_is_app` (in `EnvContext`) and the `*_is_app`/`*_not_is_app` state variants to a name which is not confusing.

## Why

*   `_is_app` is set by `EnvState.state_is_app_defined` as `True` for certain `EntryFunc`-s
    (see [app_vs_lib][FT_93_57_03_75.app_vs_lib.md], [boot_vs_start][FT_58_74_37_70.boot_vs_start.md]).

*   The name is ambiguous: is it about user code or `protoprimer` code? It is about `protoprimer`
    (whether `protoprimer` itself runs as an app via `EntryFunc` or is called as a lib).

*   The `app vs lib` distinction is documented as partially obsoleted by `boot_vs_start`
    (and the doc needs an update after [call_lib][FT_85_17_35_21.call_lib.md]) -
    so the name should be decided together with the docs, not before.

*   The name is spread into many state names (`Bootstrapper_state_*_is_app` and `Bootstrapper_state_*_not_is_app`
    for args parsing, log level, exec operation, print conf, prepare venv, final state, ...).

## What to do

*   First decide what the flag means in terms of the current docs (`boot`/`start` vs `call_lib`)
    and pick a name which says so (e.g. via `EntryFunc` instead of the vague `app`).

*   Rename the field, `EnvState.state_is_app_defined`, and the `*_is_app` / `*_not_is_app` classes together.

*   Update the naming tests (`test_naming`), ordering tests, dynamic graph tests, `local_repo` graph printer, `local_test`.

*   Update the docs (`FT_93_57_03_75.app_vs_lib.md` and the others which mention the flag).

## Considerations

*   Pros: names say what they mean.

*   Cons / risks: wide mechanical change (kernel, stand-alone `proto_kernel.py` copy, around 10 test and tool files);
    state names are used as keys (see [TODO_49_40_51_46.rename_state_names_to_final.md][TODO_49_40_51_46.rename_state_names_to_final.md]) -
    better do both renames in sequence (or at once).
