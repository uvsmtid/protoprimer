Provide a simple way to delegate `boot_env` to a plain client function for the majority of use cases,
so that `cmd_boot_env_example.py` can become almost as trivial as `cmd_start_app_example.py`.

## Purpose

`cmd_start_app_example.py` and `cmd_boot_env_example.py` are the two canonical "hello world" entry points
(see [FT_05_08_64_67.start_app.md][FT_05_08_64_67.start_app.md] and [FT_85_17_35_21.boot_env.md][FT_85_17_35_21.boot_env.md]),
but they are wildly different in size and conceptual weight:

*   `cmd_start_app_example.py` is a single function with a `print` statement -
    `EntryFunc.func_start_app` has already finished all the DAG work by the time client code runs,
    so there is nothing left to wire up.

*   `cmd_boot_env_example.py` has to define a whole `EnvState`-like `enum.Enum` (`CustomEnvState`),
    a `StateNode` subclass (`Bootstrapper_state_hello_world_printed`) decorated with `@trivial_factory`,
    wire its `_parent_states` to `TargetState.target_proto_bootstrap_completed`,
    set `forced_final_state`, and `register_factory` it -
    all just to run the equivalent one-line `print("Hello, world!")`.

In the overwhelming majority of real client code, `EntryFunc.func_boot_env` does not need a custom DAG node at all:
it only needs "run this one function after `protoprimer` finishes bootstrapping the environment".
The DAG-extension machinery (own `enum`, own `StateNode` subclass, explicit `register_factory` call) exists for
[UC_10_80_27_57.extend_DAG.md][UC_10_80_27_57.extend_DAG.md] - i.e. for clients that need to add *more than one*
node, with their own dependency edges, to the DAG. That is not the common case shown in the example.

The purpose of this `TODO` is to let `protoprimer` absorb that boilerplate itself, so a client who only wants
"call my function once the environment is ready" does not have to learn `StateNode`, `trivial_factory`,
or `register_factory` to do it.

## Analysis

The boilerplate in `cmd_boot_env_example.py` that a trivial client should not need to write:

*   `CustomEnvState` `enum.Enum` - exists only to give the state a `.name` to register under.
*   `Bootstrapper_state_hello_world_printed(AbstractCachingStateNode[int])` - exists only to adapt a plain
    callable to the `StateNode` interface (`_eval_state_once`).
*   `@trivial_factory` - exists only because `StateGraph` expects a `NodeFactory`, not a bare callable.
*   `_parent_states = ... [TargetState.target_proto_bootstrap_completed.value.name]` - always the same value
    for this use case (run after bootstrap, before `EntryFunc.func_boot_env` hands off).
*   `env_ctx.register_factory(...)` - a second, separate wiring step after `forced_final_state(...)`.

None of this is specific to printing "Hello, world!" - it would be identical for any single client callable.

## What to do

Add a `ContextBuilder.client_func(callable)` method, plus a module-level `run_boot_env_client_func(callable)`
wrapper, that:

*   Accepts a plain `Callable[[], int | None]` only - no `env_ctx` parameter, no CLI args.
    (The return type is `int | None`, not an arbitrary `ValueType`: `ExitCodeReporter.execute_strategy`,
    the strategy `boot_env` always uses, requires the final state's value to be `int` and calls
    `sys.exit(exit_code)` with it; `None` is coerced to `0`, so a plain `lambda: print(...)` still works.)
    (DECIDED: CLI args cannot be propagated here in principle - see [FT_62_88_55_10.CLI_compatibility.md]
    [FT_62_88_55_10.CLI_compatibility.md]; the entry script's CLI surface is owned by `protoprimer` itself.
    A callable needing `env_ctx` access, or needing more than one parent-state dependency, is a sign it needs
    a real `StateNode` via [UC_10_80_27_57.extend_DAG.md][UC_10_80_27_57.extend_DAG.md] instead of this shortcut -
    see `cmd_prime_env.py` below.)
*   Internally creates the equivalent of `Bootstrapper_state_*` / `trivial_factory` / `register_factory` /
    `forced_final_state(...)`, using a single fixed (constant) state name - no `CustomEnvState` `enum.Enum` is
    needed, since `_state_name`/`register_factory`/`forced_final_state` only need a plain string.
*   Allows `.client_func(...)` to be called at most once per `ContextBuilder` - a second call raises,
    pointing at [UC_10_80_27_57.extend_DAG.md][UC_10_80_27_57.extend_DAG.md] for multi-node cases.
*   Reduces `customize_env_context()` in `cmd_boot_env_example.py` to roughly:

    ```python
    def custom_boot_env_main():
        run_boot_env_client_func(lambda: print("Hello, world!"))
    ```

*   Keeps the existing explicit `enum` + `StateNode` + `register_factory` path available and documented
    (via [UC_10_80_27_57.extend_DAG.md][UC_10_80_27_57.extend_DAG.md]) for clients that genuinely need multiple
    DAG nodes with their own dependency edges - this `TODO` only adds a shortcut for the single-callable case,
    it does not replace the general mechanism.

*   Updates `cmd_boot_env_example.py` to use the new shortcut, so it stays a useful "majority use case" example
    (while possibly keeping the current explicit version elsewhere, or in this doc, as the "advanced" example).

## Considerations

*   Pros: removes the need to understand `StateNode`/`trivial_factory`/`register_factory` for the common case;
    makes `cmd_boot_env_example.py` approachable at a glance, matching the simplicity of `cmd_start_app_example.py`.

*   Cons / risks: DECIDED - a fixed constant state name is used, since `.client_func(...)` is only allowed
    once per `ContextBuilder` (a second call raises); DECIDED - the callable's return value flows through as
    the real result/exit code of the process, it is not discarded; DECIDED - `None` (e.g. from a bare
    `print(...)`) is coerced to exit code `0`, any other non-`int` value is a bug the caller must fix
    (`ExitCodeReporter` asserts `int`).

## Review of existing `boot_env` consumers

`cmd/boot_env_example` (-> `cmd_boot_env_example.py`) and `cmd/prime_env`/`./prime` (-> `cmd_prime_env.py`) are
the only two existing entry scripts using `boot_env`; everything else in `cmd/` uses `start_app`.

`cmd_prime_env.py` - is **not** a candidate for this shortcut: its `Bootstrapper_state_pre_commit_configured`
depends on three parent states (not just `target_proto_bootstrap_completed`) and calls
`self.eval_parent_state(...)` twice to read resolved context values, which requires a real `StateNode` plugged
into the DAG via [UC_10_80_27_57.extend_DAG.md][UC_10_80_27_57.extend_DAG.md]. It stays on that path unchanged.
This confirms the shortcut's scope is correctly narrow - it targets clients that just want to run one plain
function after bootstrap, not clients that need to plug into the DAG itself.
