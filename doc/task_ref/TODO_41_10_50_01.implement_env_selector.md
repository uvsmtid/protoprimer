## Description

There should be a way to delegate selection of the env to the target repo, analogous to how `python` selection is
already delegated to a selector script.

Today exactly two inputs decide which env dir is used:

*   `--env`/`-e` (`_SyntaxArg.arg_env`, `primer_kernel.py:505`) - a CLI arg, read via
    `_Node_state_selected_env_dir_rel_path_inited_is_app._select_env_conf_dir_any_path` (`:3331-3339`).
*   `ConfField.field_default_env_dir_rel_path` (`:549`) - a static field in `client_conf`, used as the fallback in
    `_select_client_local_env_dir_any_path` (`:3263-3287`) whenever `--env` was not given.

There is no third, *dynamic* input - no env equivalent of the `python`-selector mechanism already in place for
choosing the `python` executable (`ConfField.field_python_selector_file_rel_path` →
`_Node_state_python_selector_file_abs_path_inited` → `_select_python_file_abs_path`, `:564`/`:3567`/`:6295`). This
doc tracks adding that missing third input, and - because adding a third input makes no sense without first
settling how it interacts with the two that already exist (and with the local-conf symlink they feed into) - also
tracks that precedence question itself, which is currently undecided and has already produced one concrete,
reproducible bug (see [FT_03_31_63_70.environment_selection.md]).

This work is also a stated prerequisite for [TODO_96_67_95_15.cross_platform_test_grid.md]'s per-platform `dst/`
env dirs (its `## Plan` "Separate target envs per platform" sub-section, Option D): rather than hand-rolling
`dst/test_python_med_windows`-style dirs and wiring a different literal `--env` value per CI job, an env-selector
script could resolve the right platform-specific env automatically, the same way `python_selector_py3.11.py`
resolves the interpreter today.

**Spec:** [FT_03_31_63_70.environment_selection.md] is the authoritative spec for all of this - both the hook's
draft contract (`## Selection`) and, more importantly, the `## Behavior` table of outcomes per `_ExecOperation` x
"is the environment already persisted" x "does the resolved value match". That table is scoped to the
persisted-vs-selected relationship *regardless of where the selected value comes from* (`--env`, the future
selector, or the default config) - so implementing it does **not** require the env-selector hook from this doc to
exist first. That implementation work (making `op_reset`/`op_eval` actually match the table) is tracked in
[FT_03_31_63_70.environment_selection.md] instead, decoupled from and ahead of the hook work below.

### Precedence between `--env`, the future env-selector, the default-env config, and the existing symlink

**Status:** DONE (decided; implementation tracked elsewhere)

**Description:**
This was the core open question, carried over from this doc's own original notes: `--env` is meant to be the
highest priority (it is how changes get "pushed" to affect existing deployments, overwriting the symlink by
decision); below it would sit the (not yet existing) env-selector script; below that, the static
`field_default_env_dir_rel_path`. [FT_03_31_63_70.environment_selection.md] independently described exactly
this failure mode (bootstrap once with `--env`, then again without it) and proposed three prose-only approaches
(A/B/C).

**Decided:** none of A/B/C, literally. [FT_03_31_63_70.environment_selection.md]'s `## Behavior` table is the
actual resolution: there is **no automatic reconciliation**. `op_reset` is the only exec operation allowed to
deliberately overwrite a persisted env that doesn't match the resolved value; every read-mostly op
(`op_boot`/`op_start`/`op_shell`) fails loudly on a mismatch instead of silently picking a side; `op_eval` is the
one exception that evaluates the resolved value without touching persistence at all (`override`, not `failure` -
see the next sub-section below). This applies uniformly regardless of whether the resolved value came from
`--env`, the future selector, or the default field - the table doesn't distinguish the source, only whether it
matches what's persisted. [FT_03_31_63_70.environment_selection.md] is now the doc tracking the actual code
change (making `op_reset`/`op_eval` match this table).

### `--env` arg: which exec operations it actually applies to today is unclear/possibly inconsistent

**Status:** TO_FIX (confirmed: the comment is stale, not the code)

**Description:**
`-e`/`--env` is registered once on the shared `parent_argparser` (`:1597-1605`), so `argparse` attaches it to every
subcommand (`boot`, `reset`, `eval`, `shell`, `start`, `check`, `wrap`) uniformly - no per-subcommand argparser
code removes or special-cases it for any of them. But the inline comment at `_select_env_conf_dir_any_path`
(`:3336`) claims "The value is only set for `_ExecOperation.op_boot`, otherwise, this default is used," which does
not match what the `argparse` wiring actually does: `getattr(state_args_parsed,
_ParsedArg.name_selected_env_dir.value, None)` retrieves whatever `--env` was given for *any* subcommand, not just
`boot`, since the attribute exists on the namespace regardless of subcommand.

**Confirmed empirically** (this repo's own checkout, `lconf` → `dst/default_env`): `./prime eval -vvv` (no
`--env`) succeeds normally against `dst/default_env`. `./prime eval --env dst/test_python_med_linux -vvv` reaches
`_Node_state_local_conf_dir_abs_path_inited` and raises:
```
AssertionError: The symlink [.../lconf] target [dst/default_env] is not the same as the provided target [dst/test_python_med_linux].
```
This proves `--env` *is* honored for `eval`, exactly like for `boot` - the comment is simply stale (most likely
left over from an earlier version of the argparser, before `--env` moved to the shared `parent_argparser`), not a
description of a real `op_boot`-only gate. This is also live confirmation for the next sub-section below: `eval`
does feed `--env` into the same symlink-comparison code `boot` uses, rather than treating it as inert.

### Non-bootstrapping exec operations unconditionally write the symlink today

**Status:** TO_FIX (confirmed, not just suspected)

**Description:**
This doc's own original notes flag it as an open question: "In case of non-bootstrapping exec-operations like
`eval`, the value must be read from symlink. If `eval` allows `--env`, then even `eval` has to adjust the symlink
(which is not read-only)." The trace in the sub-section above confirms exactly this: `eval` does allow `--env`,
and the resulting `AssertionError` was raised from inside `_Node_state_local_conf_dir_abs_path_inited`
(`:3370-3454`) - the very code path that, with a *non-conflicting* `--env`/selector/default value (or no existing
symlink at all), would instead silently call `os.symlink(...)` and create/overwrite the symlink. That node is not
gated behind `_is_app`/`op_boot` at all, and sits upstream of `state_env_conf_file_data_loaded` (`:3486-3503`),
which `op_eval`'s own state-graph target (`state_effective_conf_data_printed`) depends on transitively. So
`eval` - whose own `argparse` help text says "Evaluate effective config (print it on `stdout`)" and which this
doc expects to be read-only - can, in fact, create or fail on the symlink exactly like `boot` does. The only part
directly exercised by the trace above is the *creation* branch specifically (the trace hit the *mismatch* branch
instead, since a symlink already existed) - but it is the same unconditional function body, with no
op-specific branch inside it, so there is no reason to expect the creation branch to behave differently for `eval`
than for `boot`.

`boot`'s path) is rejected - it's exactly what [FT_19_44_42_19.effective_config.md] already says `eval` must not
