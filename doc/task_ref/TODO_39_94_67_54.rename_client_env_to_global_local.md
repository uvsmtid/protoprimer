## Why

The kernel is half-way through the rename:

*   Already `global`/`local`:
    `ConfLeap.leap_global`, `ConfLeap.leap_local`, `PathName.path_global_conf`, `PathName.path_local_conf`,
    `ConfField.field_global_conf_dir_rel_path`, `ConfField.field_local_conf_symlink_rel_path`.

*   Still `client`/`env`:
    `ConfLeap.leap_client`, `ConfLeap.leap_env`, `PathName.path_conf_client`, `PathName.path_conf_env`
    (and constants and states derived from them: `default_*_leap_client`, `default_*_leap_env`, ...).

Result: duplicated enum members (`leap_client` vs `leap_global`) and two names for the same thing.

## What to do

*   Rename `ConfLeap.leap_client` to `global` (value) and `ConfLeap.leap_env` to `local`.

*   Consolidate with the already existing `leap_global` and `leap_local`
    (they are not really `ConfLeap`-s - see `leap_client` and `leap_env` instead).

*   Remove `PathName.path_conf_client` and `PathName.path_conf_env`
    (use `path_global_conf` and `path_local_conf`).

*   Decide on `ConfDst` naming: is `dst_*` supposed to be "conf src" (instead of "conf dst")?

*   Update docs, diagrams, and tests which use the old names.

## Considerations

*   Pros: one vocabulary in code and docs; no duplicated enum members; mostly mechanical.

*   Cons / risks:

    *   Many files change (kernel, `metaprimer`, tests, docs).

    *   `.name` and `.value` of the renamed enums may be visible in `config` output
        (dict keys and path names) - check before renaming.

    *   `env` stays in `default_env` and `--env`, `EnvState`, `state_env_conf_*` -
        decide whether these are renamed too (otherwise naming is only partially consistent).

*   Config JSON field names do not contain `client` or `env` from these enums (to be verified).
