TODO: TODO_68_40_26_10.define_env_vars_in_known_env_var_enum.md

Stop using hardcoded literals for external env var names `ZDOTDIR` and `SHELL`:
define them as named constants (the in-place TODO-s call the target `KnownEnvVar` enum).

## Why

*   There is no `KnownEnvVar` enum. The existing names are:

    *   `EnvVar` - only `PROTOPRIMER_*` vars owned by `protoprimer` (see [env_var][FT_08_92_69_92.env_var.md]).

    *   `ConfConstInput.ext_env_var_*` - external vars: `VIRTUAL_ENV`, `PATH`, `PYTHONPATH`.

*   Literals still hardcoded in the kernel: `"ZDOTDIR"` (`ShellDriverZsh`) and `"SHELL"` (`_get_shell_driver`).

## What to do

*   Choose where to define them:

    *   `ConfConstInput.ext_env_var_SHELL` and `ext_env_var_ZDOTDIR` - consistent with existing external vars (recommended);

    *   or add them to `EnvVar`.

*   **Do not add them to `EnvVar` blindly:**
    `remove_protoprimer_env_vars` (context isolation) removes *every* `EnvVar` member from the environment,
    so `SHELL` and `ZDOTDIR` (not owned by `protoprimer`) would be dropped.
    Creating a separate enum for external vars (the `KnownEnvVar` from the TODO) avoids this.

*   Replace the 2 literals and update the in-place TODO-s (the name `KnownEnvVar` in them should match the decision).

*   Tests may keep hardcoded `"SHELL"` and `"ZDOTDIR"` in `patch.dict` calls.

## Considerations

*   Pros: no magic strings; discoverable list of external env vars the kernel depends on.

*   Cons / risks: the `proto_kernel.py` copy needs to be re-synced; mixing owned and external names in one enum is confusing and (see above) unsafe.
