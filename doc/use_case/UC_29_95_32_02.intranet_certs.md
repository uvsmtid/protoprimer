# UC_29_95_32_02.intranet_certs

## Symptom

On a corporate network with a TLS-intercepting proxy, `./prime` fails while seeding the `venv`:

```
error: Failed to install seed packages into virtual environment
  Caused by: No solution found when resolving: `pip`
  Caused by: Failed to fetch: `https://pypi.org/simple/pip/`
  Caused by: error sending request for url (https://pypi.org/simple/pip/)
  Caused by: client error (Connect)
  Caused by: invalid peer certificate: UnknownIssuer

hint: Consider enabling use of system TLS certificates with the `--system-certs` command-line flag
```

## Root cause

By default `uv` verifies TLS with its own bundled Mozilla root cert bundle (`webpki-roots`), not the OS trust store.
A corporate proxy that MITM-intercepts HTTPS re-signs traffic with a corporate root CA.
That CA is typically installed in the OS trust store (managed device), but `uv` never looks there by default -> `UnknownIssuer`.

This is a network/environment condition, not a `protoprimer` bug.

## Where this hits in `protoprimer`

The failing call is the `uv venv --seed ...` invocation inside `VenvDriverUv._create_venv_impl`
(`primer_kernel.py`, mirrored as `proto_kernel.py`).
It runs *before* any dependency installation.

Config-driven `extra_command_args` (see [private_artifact_repo][FT_17_41_51_83.private_artifact_repo.md])
only reaches the later package-install step, not the `venv`-seeding step -
there is currently no `proto_kernel.json` field that threads extra args or env into `uv venv --seed`,
`uv python install`, or the `uv python dir` availability check.

## Fix: environment variables, no `protoprimer` config/code change needed

```sh
export UV_SYSTEM_CERTS=1   # current name
# export UV_NATIVE_TLS=1   # deprecated alias, same effect
```

This works without touching `proto_kernel.json` or `primer_kernel.py` because none of the three `uv` subprocess
calls in `VenvDriverUv` override `env=` - they inherit `os.environ` as-is. `protoprimer`'s internal python
re-execs only strip `VIRTUAL_ENV`, `PYTHONPATH`, and `PROTOPRIMER_*` vars, so `UV_SYSTEM_CERTS` survives every hop
down to the failing call.

Users on managed machines can set this once in their shell profile.

Diagnose first, to pick the right fix:

```sh
curl https://pypi.org/simple/pip/
```

*   Cert error only (connects, TLS fails) -> `UV_SYSTEM_CERTS=1` is enough.
*   Connection fails outright (proxy blocks `pypi.org` entirely, not just intercepts) -> need an internal mirror instead/also:
    `UV_INDEX_URL=https://<internal-mirror>/simple/`.

## `--system-certs` vs `--native-tls`

Same functionality; `--native-tls` / `UV_NATIVE_TLS` is the deprecated name, `--system-certs` / `UV_SYSTEM_CERTS`
is current. Both switch `uv` to `rustls-platform-verifier`, which delegates to the OS's own certificate verifier
(macOS Keychain, Windows cert store, `/etc/ssl` on Linux) instead of `uv`'s bundled bundle.

## Why isn't system-certs the default?

*   **Portability/determinism** - bundled certs behave identically on every machine; the OS store varies by
    machine/config, which cuts against `uv`'s hermetic-by-default design.
*   **Performance** - reading the OS cert store (e.g. macOS Keychain via the Security framework) has real
    per-handshake overhead versus parsing a static bundled bundle.

The trade-off flips exactly in the corporate-proxy case, where the only CA that can validate the connection
lives in the OS store.

## Decision: no in-tool error detection

Considered: wrap the `uv` subprocess calls, capture `stderr`, pattern-match for cert/network error markers, and
print a hint (`UV_SYSTEM_CERTS=1`, `UV_INDEX_URL=...`) on failure.

Rejected. Matching `uv`'s error text is brittle across `uv` versions, and users in managed environments can
already fix this once via their shell profile. Keep failures surfacing as a plain `CalledProcessError` ->
`RuntimeError` (existing behavior); rely on the user pasting the raw error into an LLM or this doc for diagnosis
instead of building heuristic error classification into `primer_kernel.py`.
