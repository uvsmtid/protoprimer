# FT_78_72_23_04.backward_compatibility

## Public interface

[Semantic Versioning][semver_link] (or `semver`) depends on public interface changes.

`protoprimer` public interface contains these components:

*   schema (config files)

*   CLI (see `EnvState.state_args_parsed`)

*   API (public entries in `protoprimer.primer_kernel`)

*   env vars (see `EnvVar`)

*   exit codes

### `old_proto_on_new_venv` handoff

`proto_kernel.py` is a stand-alone copy committed in client repos.
It runs before `venv` exists and then hands off to `protoprimer.primer_kernel` in `venv`.

### `old_entry_on_new_proto` handoff

Old copies of `proto_kernel.py` and of entry scripts may stay in client repos,
so they must keep working with a new `venv`.

## Baseline

The baseline is a list of commit names (ids, branches, tags) that the current code must stay compatible with.

It is set by `baseline_commit_names` in `[tool.local_contract_compatibility]` of `src/<package>/pyproject.toml`.

Commit name `HEAD` resets baseline to the current commit.
It can be replaced with a real older commit name or tag once there is a release to keep compatible with.

## Enforcement

The enforcement is implemented via:

*   the runner: `local_contract_compatibility` package

*   the compatibility tests: `test_contract_compatibility` sub-dir, run in these modes:

    *   `old_tests_on_new_changes`:

        This mode runs old compatibility tests on new changes.

        The tests and specs are taken from the baseline, so editing a test or a spec in the new tree cannot hide a break.

    *   `old_proto_on_new_venv`:

        See `old_proto_on_new_venv` handoff:
        old `proto_kernel.py` on new `protoprimer.primer_kernel` in new `venv`.

    *   `old_entry_on_new_proto`:

        See `old_entry_on_new_proto` handoff:
        old entry script on new `proto_kernel.py` with new `protoprimer.primer_kernel` in new `venv`.

    *   `new_tests_on_new_changes`:

        This is not a special mode: it is plain `pytest` on the current tree, which selects tests by their own conditions.

        It is never run by the runner with `--mode_id`, but it is defined for completeness.

        Plain `pytest` in the `py[min]/[med]/[max]` CI jobs is this mode.

*   spec-based checks via:

    *   `pydantic` for schema compatibility defined in `local_config_schema` package

    *   `cliff` for CLI compatibility

    *   `griffe` for API compatibility

## Spec-based tests

Spec-based checks are tests in `test_fast_not_mocked/test_contract_compatibility`,
so they are fast and part of the contract of a commit name.

*   `pydantic`:

    *   the `local_config_schema` package defines schema of config files

    *   the models ignore extra fields (a new config field is not a break)

*   `cliff`: CLI

    *   the spec holds literals only (nothing is taken from `protoprimer`)

*   `griffe`: API

*   public strings:

    *   `EnvVar` item values

    *   `ConfField` item values

    *   `VenvDriverType` item names

`griffe` compares only public (non-underscore) objects.

Public strings:

*   `griffe` does not see a changed value of an attribute or an enum member.

*   Custom tests with frozen values are used to verify breaking changes for values in selected enums where item value is part of the public interface.

The old spec runs against the new code, so changing something the old spec knows is a break.
Adding something new (a name, a CLI arg, a config field) is backward-compatible and must not fail a check.

`griffe` and `pydantic` require `python` > min (see [supported_python_versions][FT_84_11_73_28.supported_python_versions.md]) and skipped if not supported.

## Layout

Tests of the public interface go to `test_contract_compatibility`.
All other tests of the same perimeter (`test_slow_integrated`, `test_fast_not_mocked`) go to the sibling `test_not_contract_compatibility`,
because the baseline's copy of `test_contract_compatibility` is run against the new changes,
so it must hold only tests that check the public interface.

`test_old_proto_on_new_venv` and `test_old_entry_on_new_proto` hold the tests of the modes with the same ids.

The tests in `test_old_*` sub-dirs are skipped unless `--commit_name` is given, so only the `compat` CI job runs them.

The tests in `test_old_*` sub-dirs reuse the tests of `test_contract_compatibility` (thin files importing them), with one input swapped:

*   `old_proto_on_new_venv`: the source of `proto_kernel.py`

*   `old_entry_on_new_proto`: the entry script text, taken from the old `wrap`

A guard test in each sub-dir fails if the swap does not happen.

## Execution

*   `new_tests_on_new_changes` (plain `pytest` on the current tree):

    *   all dirs except the `test_old_*` ones, which are skipped without `--commit_name`

*   `old_tests_on_new_changes` (from the baseline worktree):

    *   `test_slow_integrated/test_contract_compatibility`

    *   `test_fast_not_mocked/test_contract_compatibility`

*   `old_proto_on_new_venv` (from the current tree):

    *   `test_slow_integrated/test_old_proto_on_new_venv`

*   `old_entry_on_new_proto` (from the current tree):

    *   `test_slow_integrated/test_old_entry_on_new_proto`

## Failure

A failed compatibility check means: the changes break backward compatibility tests in the baseline.

Possible actions:

*   fix the changes to comply

*   update the baseline

The message names the mode and the commit name.

## Runner

The runner is `cmd/test_contract_compatibility` (the `local_contract_compatibility` package).

It runs the modes which depend on the baseline:

*   `old_tests_on_new_changes`

*   `old_proto_on_new_venv`

*   `old_entry_on_new_proto`

Arguments:

*   `--package_name`: the package to check

*   `--commit_name`: overrides `baseline_commit_names`

*   `--mode_id`: the mode to run

## CI

The `compat` CI job runs the runner, one step per mode, under the `max` python only.

The job fetches the full history with tags, so any commit name in the baseline can be resolved.

A step runs even when an earlier step failed, so each mode reports its own failure.
