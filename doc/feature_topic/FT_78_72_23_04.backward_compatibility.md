# FT_78_72_23_04.backward_compatibility

## Public interface

[Semantic Versioning][semver_link] (or `semver`) depends on public interface changes.

`protoprimer` public interface contains these components:

*   schema (config files)

*   CLI (see `EnvState.state_args_parsed`)

*   API (public entries in `protoprimer.primer_kernel`)

*   env vars (see `EnvVar`)

### `old_proto_on_new_venv` handoff

`proto_kernel.py` is a stand-alone copy committed in client repos.
It runs before `venv` exists and then hands off to `protoprimer.primer_kernel` in `venv`.

### `old_entry_on_new_proto` handoff

Old copies of `proto_kernel.py` and of entry scripts may stay in client repos,
so they must keep working with a new `venv`.

## Baseline

The baseline is a list of commit names (ids, branches, tags) that the current code must stay compatible with.

It is set by `baseline_commit_names` in `[tool.local_contract_compatibility]` of `src/<package>/pyproject.toml`.

Commit name `HEAD` resets baseline to the current commit.
It can be replaced with a real older commit name or tag once there is a release to keep compatible with.

## Enforcement

The enforcement is implemented via:

*   the runner: `local_contract_compatibility` package

*   the compatibility tests: `test_contract_compatibility` sub-dir, run in these modes:

    *   `old_tests_on_new_changes`:

        This mode runs old compatibility tests on new changes.

        The tests and specs are taken from the baseline, so editing a test or a spec in the new tree cannot hide a break.

    *   `old_proto_on_new_venv`:

        See `old_proto_on_new_venv` handoff:
        old `proto_kernel.py` on new `protoprimer.primer_kernel` in new `venv`.

    *   `old_entry_on_new_proto`:

        See `old_entry_on_new_proto` handoff:
        old entry script on new `proto_kernel.py` with new `protoprimer.primer_kernel` in new `venv`.

    *   `new_tests_on_new_changes`:

        This is not a special mode - it is the default any test runs anywhere.

        This mode is not run in `test_contract_compatibility`, but it is defined for completeness.

*   spec-based checks via:

        *   `pydantic` for schema compatibility defined in `local_config_schema` package

        *   `cliff` for CLI compatibility

        *   `griffe` for API compatibility

## Spec-based tests

Spec-based checks are tests in `test_fast_not_mocked/test_contract_compatibility`,
so they are fast and part of the contract of a commit name.

*   `pydantic`: schema of config files, defined in the `local_config_schema` package

*   `cliff`: CLI

*   `griffe`: API

*   `EnvVar` names test: env vars

`griffe` compares only public (non-underscore) objects.

## Layout

Tests of the public interface go to `test_contract_compatibility`.
All other slow tests go to the sibling `test_not_contract_compatibility`,
because the baseline's copy of `test_contract_compatibility` is run against the new changes,
so it must hold only tests that check the public interface.

`test_old_proto_on_new_venv` and `test_old_entry_on_new_proto` hold the tests of the modes with the same ids.

The tests in `test_old_*` sub-dirs are skipped unless `--commit_name` is given, so only the `compat` CI job runs them.
