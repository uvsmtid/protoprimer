## Purpose

`protoprimer` is started by a user (or a script) in a wild environment it does not control.

This file collects the conditions (scenarios) which differ from the "happy path" and
describes how each is (or should be) handled.

Each scenario has a short title (to call it by name) and the following fields:

*   **Status** - prefixed by one of:
    *   `DONE` - implemented (with evidence);
    *   `TODO` - not (fully) implemented (what to do, dependencies);
    *   `TBD` - something has to be confirmed first (a hypothesis not verified by a test or an experiment);
    *   `SKIP` - decided not to be done (with the reason).

*   **Problem** - what happens and why it matters.

*   **Options** - possible ways to solve it (for a scenario which is not `DONE`, this may be the only solution-related section).

*   **Solution** - the current/final implementation taken out of **Options**:
    *   for `DONE`: how it is implemented
    *   for `SKIP`: what is done instead (if anything)
    *   for `TODO`/`TBD`: not present until an option is selected (**Options** only)

*   **References** - classes, states, functions, docs, standard `python` modules/flags.

Titles carry the same prefix as **Status**.

## Background

The mechanisms that all invocation scenarios rely on:

*   `protoprimer` starts with an unpredictable `python` and re-executes itself (`os.execve` in `_switch_python`)
    through a monotonic sequence of `_StateStride`-s
    (see [python_executable][FT_72_45_12_06.python_executable.md]):
    *   `stride_py_arbitrary`
    *   `stride_py_required`
    *   `stride_py_venv`
    *   `stride_deps_updated`
    *   `stride_src_updated`

*   The only state passed between the restarts is carried by env vars:
    *   `PROTOPRIMER_PY_EXEC`: the current stride
    *   `PROTOPRIMER_PROTO_KERNEL`: abs path to the stand-alone `proto_kernel`
    *   `PROTOPRIMER_START_ID`: see [env_var][FT_08_92_69_92.env_var.md] or `EnvVar` enum

*   Every restart (`_switch_python`) runs the next `python` with `-I`
    ([isolated_python][FT_28_25_63_06.isolated_python.md]).

    Per the [`python` docs][python_cmdline_I]:
    *   `-I` implies `-E`: ignores `PYTHON*` env vars
    *   `-I` implies `-s`: no user site dir
    *   `-I` puts neither the script dir nor the cwd into `sys.path`
    *   `-I` does **not** hide the system `site-packages` of the interpreter's own prefix
    *   `-I` does **not** touch non-`PYTHON*` env vars: `PATH`, `VIRTUAL_ENV`, `PIP_*`, `UV_*`, ...

*   The very first process is **not** under `-I` (it is started by the shebang line / the user):
    *   it must only import the standard library
    *   today: all module-level imports of `primer_kernel` are `stdlib`

*   `venv` detection: `sys.prefix != sys.base_prefix` (`_is_venv`), see [PEP 405][pep_405].

## Testing

Each scenario is tested in a container: a pinned public image with `python` plus explicit setup steps.

*   The test code is a separate test perimeter (see [test_perimeter][FT_83_60_72_19.test_perimeter.md]):
    *   test dir: `src/protoprimer/test/test_protoprimer/test_invoke_condition/`
    *   one file per scenario: `test_invoke_condition_NN.py` (`NN` = the number in the table above)
    *   fixtures (the container helper, the scenario registry): the `local_test` package
    *   the registry is the `InvokeCondition` enum: one item per scenario title, with the same number as in the table

*   Why containers:
    *   every condition is reproducible from scratch (never from a developer machine)
    *   the container has no test tooling (no `pytest`), so nothing contaminates the condition under test
    *   the product code runs for real: no test-only hooks (`_is_test_run` is false, `EnvVar.var_PROTOPRIMER_MOCKED_RESTART` is unset)

*   How a test works:
    *   the test runs on the host, creates a clean tree (tracked and untracked-but-not-ignored files, without `venv`/`lconf`/`cache`)
    *   it starts a container from a pinned public image (nothing is baked into images, no special images are maintained)
    *   it generates one or more shell scripts (steps) and executes them in the same container (`docker exec`)
    *   it asserts the observable outcome on the host: exit code, `protoprimer` own messages (not text of `apt`/`pip`/`uv`), files

*   What is asserted - the **current** behavior, for any status:
    *   `DONE`: the documented behavior
    *   `SKIP`: the accepted behavior (it may be not ideal, but it is asserted so that a change is noticed)
    *   `TODO`/`TBD`: the behavior as it is today, with a comment `TODO: FT_64_09_03_66.invoke_condition.md: <hint>` before the line to fix

*   There is no `xfail`/special filtering by status: all the tests pass in CI, the status is tracked by this file and the comment in the test.

*   Tests are pinned to specific image versions and are examples of the scenario

### SKIP: `py_too_old_for_kernel`

**Status:**

*   SKIP: `python` < 3.7 is not supported - the `SyntaxError` is accepted (not made user-friendly).

*   Why it is a `SyntaxError` and not a message from `_ensure_min_python_version`:
    *   `primer_kernel.py` starts with `from __future__ import annotations` (new in `python` 3.7)
    *   on `python` < 3.7 the module fails with `SyntaxError: future feature annotations is not defined` at compile time
    *   that happens before `_run_process` calls `_ensure_min_python_version`

*   Dependencies:
    *   [supported_python_versions][FT_84_11_73_28.supported_python_versions.md]: min = 3.7

**Problem:**

*   `./prime` is started by `python3` which is 3.6 or older (e.g. an old LTS distro) or `python` is `python2`.

*   The user sees a syntax error pointing to the `from __future__` line of `proto_kernel`, not a hint what to do.

**Options:**

*   Accept the `SyntaxError` and document the min version (the comment right above the failing line already states the min version).

*   Add a tiny version guard (parseable by old `python`) to the [entry_script][FT_75_87_82_46.entry_script.md] template
    (`_generate_entry_script_content`) which checks `sys.version_info` before the kernel is imported:
    *   the only place where a friendly message is possible
    *   does not help when `proto_kernel` is run directly (without an entry script)

*   Put a version-check stub above `from __future__ import annotations` (to run before the failing line):
    *   it cannot work: only comments, blank lines and the module docstring may precede a `from __future__` import,
        so no statement can run before it

*   Make the kernel itself parseable and importable by `python` < 3.7:
    *   drop `from __future__ import annotations`:
        *   it is load-bearing for 3.7-3.10 as well (verified by running a copy without it):
            *   3.9: `TypeError: unsupported operand type(s) for |` on `str | None`
            *   3.10: `NameError` on a forward reference like `env_ctx: _EnvContext`
        *   so all annotations have to be rewritten: ~72 lines with `X | None` and ~59 with `list[...]`/`dict[...]`/`tuple[...]`
    *   replace `contextvars` (3.7+ stdlib module) which fails first on 3.6 once `__future__` is dropped
    *   move the version check to the very top and `os.execv` a newer `python` or fail with a human message

**Solution:**

*   The first option: accept the `SyntaxError`.

*   Reasons for not taking the other options:
    *   `python` 3.6 is EOL and not tested (see [supported_python_versions][FT_84_11_73_28.supported_python_versions.md])
    *   supporting it has a large blast radius (see above) for no real user
    *   a guard in the entry script covers only part of the invocations
    *   a stub above the `from __future__` import is not possible at all

*   Implementation: already in place - the `supported_python_versions` comment in `primer_kernel.py`
    right above `from __future__ import annotations` (the line which fails).

**References:**

*   `_ensure_min_python_version`
*   `_run_process`
*   `sys.version_info`
*   `contextvars`
*   [bootstrap_precondition][FT_22_11_94_65.bootstrap_precondition.md]
*   [supported_python_versions][FT_84_11_73_28.supported_python_versions.md]
