# FT_47_61_24_68.combined_coverage

Combine the test coverage of all test jobs into one number.

## Why

*   Jobs run different tests on different OS-es, `python` versions, and places
    (containers, baseline worktrees).
*   Any single job sees code as "uncovered" if that code only runs elsewhere.
*   One combined number does not depend on which job reaches which line.

## Principle

*   Every test job measures its own coverage and uploads it to `coveralls.io` as a parallel part.
*   `coveralls.io` merges the parts - our jobs do not combine anything.
*   One more job tells `coveralls.io` that all parts are uploaded - only then the number is calculated.

## Why these choices

*   `lcov` reports with repo-relative paths: they merge across OS-es and checkouts.
*   The same `build-number` (the commit) in every job: jobs are in separate workflows,
    a run id would split them into separate builds.
*   The closing job is a `push` workflow: `workflow_run` only fires from the default branch.
*   The closing job waits for all test workflows: closing early would publish partial coverage.
*   A failed job uploads nothing: the number drops (the failure is not hidden).

## Where to find

*   Upload: search `parallel: true` in `.github/` (test env actions, contract and invoke workflows).
*   Tests under `coverage`: `cmd/report_coverage`.
*   Closing: `cover_finish.yaml` and `cmd/wait_for_workflow_runs`.
*   Paths: `relative_files` and `[paths]` in `gconf/coveragerc.ini`.

## Code run in other places

*   Opt-in: `PROTOPRIMER_COVERAGE_DIR` env var (`coverage_dir_env_var`).
*   Contract tests: the current code is measured while the old tests run (`run_mode_tests.py`).
*   Containers: a `sitecustomize.py` hook (`container_hook_installer.py`),
    because isolated `-I` mode ignores `PYTHONPATH`.
    See [isolated_python][FT_28_25_63_06.isolated_python.md].
*   `os.execve` drops the data of the process it replaces: only the last process of a chain is measured.
